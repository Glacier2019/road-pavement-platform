## 2. 需求覆盖缺口（HIGH）

### HIGH-1：FR-004 无任务承接

**原文**：
> FR-004：对 `source_ready_not_imported` 的表，系统 MUST 能指出**具体缺哪一次导入**
> （哪个后缀、哪个段），而不只说"没数据"。

**现状**：tasks.md 中 0 处引用 FR-004。
data-model.md 定义了 `segments` / `suffixes` 字段，但**没有一条任务要求把它们算出来并渲染**。

**为什么重要**：这条正是本特性的**核心价值**。判出"源已具备"只完成一半，
用户真正需要的是"跑哪一次导入"。若 segments/suffixes 留空，
页面只能说"源已具备"，用户仍要自己去翻目录 —— 缺口没真正闭合。

**建议**：把 T024 从"action 文案"扩为「action 文案 ＋ 指出来源段与后缀」，
并在 T015 的响应契约里把 segments/suffixes 标为**非空要求**（当空因是 `source_ready_not_imported` 时）。

### HIGH-2：SC-006 无任务承接

**原文**：
> SC-006：页面加载后 3 秒内可读出"我的模块有几张空表、先动哪张"。

**现状**：tasks.md 中 0 处引用。T034 只说"跑七组验收"，未含性能判据。

**为什么重要**：SC-006 是**唯一的可用性判据**。
它还有一层没写出来的含义：`/tables` 页现在要**多取两路**（M3 表事实 ＋ M2 段能力），
若 M2 的目录扫描慢、或每次请求都重扫，页面会变慢 —— 这正是 SC-006 要防的。

**建议**：在 T034 增补一条可观测量：计时 `curl -w "%{time_total}"` 对
/gw/v1/catalog/gaps，断言 < 3s；并在 T005 注明目录扫描需在**一次**请求内完成（不得每段一次 stat）。

## 4. 措辞一致性（MEDIUM-2）

**发现**：`source_present=true` 的对外措辞在三处表述有细微出入：

- 契约 `v1-design-capabilities.md`：必须说「源已具备」，**不得**说「可以导入」
- tasks.md T028：必须说「源已具备」，**不得**说「可以导入」
- spec.md：用的是「源已具备·未导入」（含「·未导入」后缀）

三者含义一致（都不承诺导入会成功），但**字符串不完全相同**。
若实现里用字符串匹配做测试，会因这个差异漏测。

**建议**：以契约的「源已具备」为唯一规范措辞，spec 的枚举名 `source_ready_not_imported`
作为机器标识保持不变。页面文案按契约。**不需要改文件**，实现时按此执行即可。

## 5. 未被任何用户故事覆盖的边界情况（MEDIUM-3）

spec 列了 5 条 Edge Case，核对它们的任务归属：

| Edge Case | 承接 | 结论 |
|---|---|---|
| 表空但有分区 | T001（基线）＋ table_census 既有实现 | ⚠️ **无独立任务** |
| 表有行但全是垃圾 | 无（**有意不覆盖** —— 明确划归 M4） | ✅ 正确不覆盖 |
| 同一段名对应多张表 | T004 ＋ T013 | ✅ |
| 空因会变 | T025 | ✅ |
| 模块登记与实测不符 | 无 | ⚠️ **无任务** |

**关于"表空但有分区"**：这条**已由既有代码满足**（table_census 只查父表），
但 tasks 里没有一条**回归测试**钉住它。未来的改动可能无意中改坏。

**关于"模块登记与实测不符"**：`phase` 字段取自模块登记表，但**没有任何任务**
验证"登记说骨架、实际已通"这种情况会被如实呈现。

**建议**：并入 T031（已是要更新 test_console.py 的那条），加两个断言即可。
