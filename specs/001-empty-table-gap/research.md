# Phase 0 Research: 空表缺口盘点与接入优先级

本文解决 `plan.md` 里三个标记为 `(?)` 的落点问题。每条都是**查了代码/实库之后**的结论，
不是设计偏好（宪法原则 III：实库 > 文件 > 文档）。

---

## R1: 「段 ↔ 表」的映射真源放哪？

### Decision

**不新建映射表。** 用既有的两条约定拼出映射，并把例外**显式登记**在 M2：

1. **默认：段名 == 物理表名。** 这不是我定的 —— `road_geometry_ir.v0.3.schema.json`
   的 `segment` 定义里**明文写着**：
   > 几何段名 —— 一律用 GE 域**物理表名**，使「段 ↔ 表」映射唯一且可自动核对（不另造一套别名）

2. **已登记的唯一例外：`design_control` 是「1 段 ↔ 9 表」的段组。**
   同一处 schema 里也写明：它是**关键字驱动**的文件，9 张表在源文件里同属一个 `.CTR`，
   拆成 9 个段会让「一个文件 → 一个段」的对账断掉。
   已实测：这 9 张表（slope_segment / ditch_segment / standard_cross_section /
   roadbed_trench / structure_control / earthwork_composition / land_use_width /
   extra_fill / design_control_text）**全部存在于实库，也全部在 `ALL_TABLES` 里**。

### Rationale

- 我一开始想「在 M3 或 M6 里新写一张 `SEGMENT_TO_TABLES` 表」。**放弃**，因为：
  它会是**第四份**对同一件事的陈述（另三份：IR schema 的约定、`_IMPLEMENTED_SUFFIX`
  的后缀→段、`design_import` 里逐段的 `tx.insert(...)`）。
  本仓库已经因为"手抄的表会漂"栽过 —— `_IMPLEMENTED_SUFFIX` 的注释里明确记着：
  「这张表曾漏掉 .ctr/.tf/.lj 三个**已经实现**的后缀，导致它们被标成 pending（表是手抄的，就会漂）」。
- 复用既有约定，则映射**天然与解析器同步**：新增一个段时，段名本身就是表名，
  不需要任何人记得来改第二处。

### Alternatives considered

| 方案 | 否决理由 |
|---|---|
| 新建声明式 `SEGMENT_TO_TABLES` 映射 | 变成第四份陈述，必然漂；且没有东西能强制它与 `tx.insert` 一致 |
| 从 `design_import` 的 SQL 调用里自动抽取 | 靠静态解析 SQL 反推映射，脆且难懂；且段可能落 0 行（合法）时抽不出来 |
| 让 M2 直接返回「段 → 已写入的表」 | 那要求 M2 知道**实库**行数 ⇒ M2 碰存储，违反硬线 II |

### ⚠ 落实现必须遵守（否则本决策退化为猜测）

**必须有一条测试钉住「例外清单是完整的」**：
遍历所有段，凡「段名 ≠ 任何物理表名」的，必须在显式例外表里登记；
反之例外表里的每一项必须真实存在于 `ALL_TABLES`。
漏登记的段会被判成"没有对应表"⇒ 静默消失（正是宪法原则 V 的"静默丢数据"）。

## R2: M2 的「源文件在不在」接口该长什么样？

### Decision

M2 新增 **`GET /v1/design/capabilities`**，返回**每个段**的三元组：

```json
{
  "segments": [
    {"segment": "earthwork_transfer", "implemented": true,
     "suffix": ".tsftxt", "kind": "土石方调配文件（.tsf 转换文本）",
     "source_present": true, "source_file": "052201341…调配文件.tsftxt"},
    {"segment": "geometry_point", "implemented": true,
     "suffix": ".3DR", "kind": "横断面三维数据文件",
     "source_present": false, "source_file": null}
  ],
  "project_dir": "<脱敏后的目录名>",
  "checked_at": "2026-09-25T…"
}
```

### Rationale

- **这三件事只有 M2 同时知道**：`IMPLEMENTED` 在它肚子里、`SEGMENT_FILES` 在它肚子里、
  导入目录也只有它在读。让别处去猜，就会猜错。
- **必须是接口而不是共享库**：M6 若 `import adapters.weidi` 去读 `IMPLEMENTED`，
  就造成了 M6 → M2 的**代码依赖**，违反硬线 II 第 3 条「跨模块只认契约」。
  走 HTTP 才是契约。（这也是为什么 M6 已有的 `/v1/catalog` 是转发 M3 而不是 import M3。）
- **`source_present` 必须现算**（每次请求扫一次目录），不能缓存进常量 ——
  源文件是**会出现的**（这正是 SC-004 要验的：接完一条链后无需改代码）。

### Alternatives considered

| 方案 | 否决理由 |
|---|---|
| M6 import M2 的适配器读 `IMPLEMENTED` | 造成代码依赖，破坏"模块可拔插"；M2 换实现就崩 M6 |
| 写进配置文件由人工维护 | 又一个手抄的表，必然漂；且"源在不在"是**环境事实**，不是配置 |
| 复用 M2 已有的 `/stats` | `/stats` 是计数器快照（运行时埋点），语义不同；且它不含"源在不在" |

### ⚠ 已知边界

`source_present` 只说明**磁盘上有这个后缀的文件**，**不**保证它能解析成功。
契约与页面措辞都必须说成"源已具备"，**不得**说成"可以导入成功"。
把前者说成后者，就是给用户一个会落空的承诺。

## R3: 优先级排序的精确判据与权重

### Decision

稳定排序，**依次**比较三个键（前面的分出胜负就不看后面的）：

| 序 | 键 | 取值 | 方向 |
|---|---|---|---|
| 1 | `action_cost` | 所需改动模块数（1 / 2 / 3+） | **升序**（改动越少越先做） |
| 2 | `source_ready` | 源是否已具备（true / false） | **true 优先** |
| 3 | `domain_order` | 域序 GE→SU→RE→LO→WE→TE→DE | 升序（按数据流方向） |

同三维都相同时，以 `table` 名**字典序**决胜 ⇒ 排序**完全确定**，
同一次输入必得同一次序（可复现，满足 plan 的确定性约束）。

### Rationale

- **键 1 放最前**：改动模块数是"这条链要拉几个组一起干"的直接代理。
  改动 1 个模块的（如五个土方段：源在、解析器已实现、只需跑一次导入）
  应当排在"要动 3 个模块"的前面。
- **键 2 第二**：源已具备意味着**不需要等外部提供**，可立即开工。
  注意它**不是**第二关键字之前的决胜项 —— 源在但代价高，仍应排后。
- **键 3 用域序而不用"重要性"**：域序是平台上**已有且公认**的（架构图 D 的七域数据流方向），
  不需要我再引入一个主观量表。"重要性"这种词无法复核，会变成不可证伪的排序。

### Alternatives considered

| 方案 | 否决理由 |
|---|---|
| 手工给每条打分 | 不可复核（SC-003 要求复核者能独立复算出同一次序） |
| 按表数多少排序 | 表多的模块不一定更该先做；且与"能不能开工"无关 |
| 按域序**单独**排序 | 会得出"GE 域 9 张先做"，但其中几张要等外部设计文件，做不了 |

### ⚠ 与 SC-003 的关系

SC-003 要求「每条都有判据，复核者能仅凭判据独立复算出同一次序」。
上面的三键排序**天然满足**：判据即三个键的取值，谁都能重算。
**故不许**在实现里加"少数手工调序" —— 那会让 SC-003 无法成立。
