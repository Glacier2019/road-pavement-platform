# Feature Specification: 空表缺口盘点与接入优先级

**Feature Branch**: `001-empty-table-gap`
**Created**: 2026-09-25
**Status**: Draft
**Input**: 平台 62 张逻辑表里有 26 张没有任何数据。要把"哪些表是空的"变成"每条空链该谁接、接到什么程度算接完"。

## 背景与问题

`/tables` 页已经能回答**哪些表是空的**，但回答不了**为什么空**、**该谁去接**。
没有这三件事，空表就只是一片红，读的人不知道该动哪一根线——这正是
`.specify/memory/constitution.md` 原则 V「『没去看』≠『看了没有』」要防的情况。

实测（2026-09-25，实库 + `/v1/catalog/tables`）：

- 逻辑表 **62**：有数据 **36**、空 **26**（占 42%）
- 空表**不是均匀分布**，而是集中在 6 个模块：
  M2 十七张、DE 域五张、SU 域四张、TE 域三张、M8 三张、M4/M5/M7/M9 各一至二张
- **最要紧的一条**：有一部分空表，**源文件就在磁盘上、解析器也已实现、测试也全绿**，
  但表里 0 行——因为**那些导入从来没在这个库上跑过**。
  实测例：`earthwork_transfer`（.tsftxt 调配过程）、`borrow_pit`、`spoil_pit`、
  `earthwork_haul_stat`、`earthwork_fill_stat` —— 五个段的适配器都在
  `weidi/__init__.py` 的 `IMPLEMENTED` 里，对应 `.tsftxt` 文件在
  `docpipe/materials/纬地工程项目文件/` 里真实存在，而实库这五张表全是 0 行。

**因此本特性的核心不是"写更多的解析器"，而是：先分清 26 张空表各自属于哪一类，
再按"离可演示链路多远"排序。** 写错这一层，就会去做已经做完的事。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一眼看出每张空表的"空因" (Priority: P1)

作为接手某个模块的同学，我打开表盘点页，看到的不应只是"这张表 0 行"，
而应是"这张表为什么 0 行、归谁、接完长什么样"。这样我不必读完 1400 行手册
才知道自己该从哪下手。

**Why this priority**：这是把"红"变成"待办"的最小一步，且**不需要写任何解析器**
——全部信息已经在实库和 catalog 里。

**Independent Test**：给任意一张空表，系统能报出它的空因分类与归属模块；
对已实现的段（如 `earthwork_transfer`），必须报"源在、解析器已实现、只是没导入"，
而**不得**报"适配器未实现"。

**Acceptance Scenarios**:

1. **Given** `earthwork_transfer` 在实库 0 行、`.tsftxt` 在磁盘上、适配器已在
   `IMPLEMENTED` 里，**When** 查询该表状态，**Then** 空因为"源已具备·未导入"，
   **不是**"适配器未实现"。
2. **Given** `test_result` 在实库 0 行且平台没有任何试验检测数据源，
   **When** 查询该表状态，**Then** 空因为"源缺失·待接入"。
3. **Given** `alarm_record`（M8 输出表），**When** 查询，**Then** 空因为
   "上游未产出"——它要等 M8 先算出告警，不是等谁去采集。
4. **Given** 一张已有数据的表，**When** 查询，**Then** 如实报"有数据"，
   **不**给它编造一个空因。

---

### User Story 2 - 按"离可演示链路多远"排序 (Priority: P2)

作为排期的人，我要一条**有依据的**优先级，而不是"SU 离主链近"这种直觉。

**Why this priority**：排序是排期与分工的输入。没有它，26 张表会变成
"都很重要"＝"都不急"。

**Independent Test**：给出排序后，能用"接完这条链需要动几个模块"来复核每条的位次。

**Acceptance Scenarios**:

1. **Given** 两条候选链，**When** 比较，**Then** 按"所需改动模块数少者优先"
   及"已有源文件者优先"稳定排序，同分时以域顺序（GE→SU→RE→LO→WE→TE→DE）决胜。
2. **Given** 排序结果，**When** 复核，**Then** 每条都写明**判据**，
   不得只给名次。

---

### User Story 3 - 接完一条链后，缺口统计自动更新 (Priority: P3)

作为验收的人，我要"接完"这件事**由数据自己说话**，而不是靠谁在文档里打个勾。

**Independent Test**：跑通一条链后，重新盘点，该表由空转有数据，空表总数相应下降。

**Acceptance Scenarios**:

1. **Given** 一条链刚接完，**When** 重新盘点，**Then** 该表 has_data 由 false 变 true。
2. **Given** 有人把数据删了，**When** 重新盘点，**Then** 它如实变回空表——
   **不得**因为"文档里说过它接完了"而继续报有数据。

### Edge Cases

- **表空但有分区**：`wim_axle_record` 若清空，父表 0 行而 39 个分区仍在——
  必须报"父表空"，**不得**因为分区存在而报有数据。
- **表有行但全是垃圾**：`row_count > 0` 判"有数据"**不校验内容质量**；
  质量由 M4 的 `truth_flag` 管。本特性**不得**越界判质量。
- **同一段名对应多张表**：`.ctr` 段落进 9 张表、`.tsftxt` 一段落 6 张表——
  判定必须按**表**逐张给结论，不能因"这个段实现了"就判定它下面每张表都已具备源。
- **空因会变**：今天"源缺失"的段，明天可能拿到源文件。空因**必须现算**，
  不许在代码里写死一张映射表。
- **模块登记与实测不符**：M9 登记表里写"骨架"，但某表其实已通——
  以实测为准，并让不符处可见。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：系统 MUST 能对任意一张逻辑表报出**空因分类**，取值限于：
  `has_data`（有数据）、`source_ready_not_imported`（源已具备·未导入）、
  `source_absent`（源缺失）、`upstream_pending`（上游未产出）、
  `module_not_built`（模块未实现）。
- **FR-002**：空因 MUST **现算**，来源为实库行数 ＋ 适配器 `IMPLEMENTED` 清单 ＋
  源文件是否在磁盘上。MUST NOT 在代码中维护一张静态的"表→空因"映射表。
- **FR-003**：系统 MUST 报出每张空表的**归属模块**，取自 M3 `TABLE_OWNER`（唯一真源），
  MUST NOT 在页面或 M6 里另抄一份。
- **FR-004**：对 `source_ready_not_imported` 的表，系统 MUST 能指出**具体缺哪一次导入**
  （哪个后缀、哪个段），而不只说"没数据"。
- **FR-005**：判定 MUST 区分"该段已实现但源文件不存在"与"源在但适配器未实现"——
  两种情况的可行动作完全不同。
- **FR-006**：系统 MUST 提供**有判据的**优先级排序，判据至少含：
  ①所需改动模块数 ②源文件是否已具备 ③所属批次（P1–P4）。
- **FR-007**：空表清单与优先级 MUST 经 M6 出口暴露，M9 经 `/gw` 读取；
  M9 MUST NOT 直连数据库（宪法原则 II）。
- **FR-008**：任何一处判定逻辑的改动 MUST 破坏至少一个契约测试（否则该判定无法验证）；
  每条新增判定 MUST 配元测试（宪法原则 V）。
- **FR-009**：系统 MUST NOT 因"文档说某表应已接入"而报有数据；
  一律以实库 `count(*)` 为准（宪法原则 III）。
- **FR-010**：模块归属或空因**无法确定**时，系统 MUST 如实报 `unknown` 并说明原因，
  MUST NOT 猜一个填上。

### Key Entities

- **空表缺口条目**：一张逻辑表 ＋ 行数 ＋ 空因 ＋ 归属模块 ＋ 所属批次 ＋ 建议动作。
- **段（Segment）**：纬地设计文件里的一个语义单元（如 `earthwork_transfer`）。
  **段名 ≠ 表名**，一个段落进一至多张表；这是本仓库已两次踩坑的混淆点。
- **导入能力清单**：`IMPLEMENTED`（真做了的）与 `CAPABILITIES`（声称支持的）。
  两者**故意不同**，差异如实反映进度。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：26 张空表 **100%** 有明确的空因分类，无 `unknown` 残留
  （若确有个别无法判定，须在验收时逐条说明，不得默认放过）。
- **SC-002**：已实现的五个土方段（`earthwork_transfer`/`borrow_pit`/`spoil_pit`/
  `earthwork_haul_stat`/`earthwork_fill_stat`）**全部**被判为
  `source_ready_not_imported`，**零张**被判为"适配器未实现"。
- **SC-003**：优先级排序**每条都有判据**，且复核者能仅凭判据独立复算出同一次序。
- **SC-004**：接完任意一条链后重新盘点，对应表由空转有数据，**无需改任何代码**。
- **SC-005**：契约测试 12/12 保持全绿，新增判定配元测试。
- **SC-006**：页面加载后 3 秒内可读出"我的模块有几张空表、先动哪张"。

## Assumptions

- 空因分类的五种取值**够用**；若实测出现第六种，先归入 `unknown` 并说明，
  不擅自扩展枚举（扩枚举要走契约变更）。
- "源文件是否在磁盘上"以**仓库内已知的素材目录**为判据
  （`docpipe/materials/纬地工程项目文件/`）；生产环境该路径由配置给出。
- 本特性**不写任何新解析器**——只做"盘点 + 归因 + 排序"。
  新解析器是各模块自己的事。
- 优先级排序的"批次"取自 M9 模块登记表的 `phase` 字段（唯一真源）。
