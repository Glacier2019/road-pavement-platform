# 规格修订 R1：`source_present` 的真源不是磁盘，而是 `design_file`

**日期**: 2026-09-25 ｜ **触发**: 实现 T005 时实测发现 ｜ **影响**: FR-002、SC-002、契约

## 实测发现（写实现时撞上的，不是推演出来的）

原规格假设：M2 有一个**持久的工程文件目录**，扫一下磁盘就知道源在不在。

**实测是错的**。M2 的导入入口是 `POST /v1/design/import`（**上传**）：

```python
# app.py:569
with tempfile.TemporaryDirectory(prefix="rp-design-") as td:
```

文件进**临时目录**，请求结束即销毁。服务端**没有**任何持久的设计文件目录，
compose 也没挂载 docpipe/materials/。

⇒ 若按原设计实现，source_present 会**恒为 false**，
   五个土方段会被判成 source_absent（"源缺失·待接入"）——
   **正好是 SC-002 明令禁止的那个错**。而且它不报错，看起来很合理。

## 真正的证据源：design_file 表

design_file 已记录了**每次导入收到过哪些文件**，且带 parse_status。实测：

```
 code |      file_kind_name       | parse_status |         file_name
------+---------------------------+--------------+------------------------------
 101  | 平面线形文件(*.PM)        | ok           | 毕设.pm
 ...  |                           |              |
 118  | 横断面三维数据文件(*.3DR) | absent       | 横断面绘图.3DR
      | 土石方调配文件(*.TSF)     | pending      | 052201341…土石方调配文件.tsf
      | 涵洞数据文件(*.hda)       | pending      | 毕设.hda
```

## ★ 由此得到的更准确结论（比原规格更锐利）

| 表 | 实库行数 | 真因 | 原规格怎么判 |
|---|---|---|---|
| earthwork_factor | **1** | 有数据 | 一致 |
| earthwork_transfer 等**五张** | **0** | **.tsftxt 从未被上传过** —— 实库只有原始 .tsf（pending，因为它是 Access 二进制，需先跑转换器） | 原规格说"源已在磁盘上"，**不准确** |

**原规格把它写成"源已具备·未导入"，暗示"跑一次导入就行"。实测不是**：
还差一步 —— 必须先跑 tools/tsf2txt.py 把 .tsf 转成 .tsftxt，再上传。
少了这一步，任何人按页面提示去"跑一次导入"都会失败。

这正是宪法原则 V 要防的：一个**看起来可执行、实际会落空**的建议动作。

## 修订

### FR-002（空因必须现算）—— 措辞收紧

原：来源为「实库行数 ＋ 适配器 IMPLEMENTED 清单 ＋ **源文件是否在磁盘上**」

改为：来源为「实库行数 ＋ 适配器 IMPLEMENTED 清单 ＋ **design_file 里登记过的收到记录**」。
design_file 是"我们**收到过**什么"的唯一真源（宪法原则 III 意义上的证据）。

### 空因枚举——增补第六类

新增 `source_needs_conversion`（源已收到·待转换）：

  row_count = 0 ∧ 对应后缀的文件已收到 ∧ 该文件的 parse_status = pending

建议动作从"跑一次导入"改为 **"先跑 tools/tsf2txt.py 转换，再导入"**。

⚠ 这**不是**擅自扩枚举 —— 规格 Assumptions 里写明"若实测出现第六种，
先归入 unknown 并说明，不擅自扩展枚举（扩枚举要走契约变更）"。
本修订即是那次契约变更，故正式登记在此，并同步改契约文档。

### SC-002——判据不变，但**判对的理由变了**

SC-002 仍要求五个土方段**不得**被判为"适配器未实现"。这一点现在是**更强**的：
它们正确分类不是 source_ready_not_imported，而是 source_needs_conversion。
SC-002 的硬断言改为：**零张**被判为 module_not_built **或** source_absent。

### 对 plan.md 的影响

T005 的"扫磁盘"改为"查 design_file"。
**但这产生一个硬线问题**：design_file 在**数据库**里，M2 查库越线吗？

→ 查证：**M2 是七域业务数据的唯一写入方**，它本来就用 WriteDao 写库。
  所以 M2 读自己写入的 design_file **不越线** —— 硬线约束的是 M3 之外的**读**路径
  与 M9 的直连，不是 M2 对自己写入记录的查询。

## 教训（写进提交信息）

规格里"源文件就在磁盘上"这句话，是我**看着仓库里的 docpipe/materials/ 目录**
写的 —— 那是**开发机上的素材目录**，不是**运行中服务的输入目录**。
两者同名同内容，但一个在仓库里、一个在容器里。我把前者当成了后者。
这正是"没去看 ≠ 看了没有"：我看了目录，但没看**服务是怎么拿到文件的**。
