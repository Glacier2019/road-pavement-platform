**Feature Branch**: `002-station-baseline-geometry`

**Created**: 2026-09-27

**Status**: Draft

**Input**: 用户描述：「桩号是基础，客观存在的，路段可能不是很确定，路段长度不定，另外不是所有路段加起来可以覆盖整条路线桩号」＋「需要」

**前置**：feature 001（空表缺口归因）已完成，`geometry_point` 是唯一剩余缺口。

> ## ⛔ 重大更正：本 spec 的一个核心前提被推翻
>
> 本 spec 初稿写「`geometry_point` 判定为 `module_not_built · 该段写适配器`」。
> **这是错的。** 实测复核（`build_ir()` 实跑）：
>
> ```json
> [{"segment": "geometry_point", "reason": "source_absent", "detail": null}]
> ```
>
> **真实原因是 `source_absent`（源里没有这个文件），不是 `module_not_built`（适配器没做）。**
> 二者含义不同：**前者去做适配器也导不出东西来。**
>
> 依据（`scaffold/contracts/design-import/README.md` 第 429–439 行）：
> `geometry_point` 的源是 **`.3DR` 横断面三维数据文件**（教程 §13.15），
> **本工程未生成**。`.GTM` 一度被指向为来源，是错的 —— 它是**索引**（二进制，
> 记数模边界框 + 路径 + 大小），不含逐桩坐标。
>
> 且该 README 已明确 `geometry_point`（A15）**是派生缓存**：
> 「由 A12（`alignment_element`）+ A13/A14 **逐桩算出**」，
> 「有理由存（缓和曲线要数值积分，逐桩重算代价高），是**合理的缓存**而非冗余；
> 但必须满足两条：① **可重建** ② 与 A12 同批次生成」。
> 契约测试 `test_design_import.py:821` 已**显式钉死**这一判定。
>
> ### 这对本 spec 意味着什么
>
> `geometry_point` **不是**「缺一个解析器」，而是「缺一个**派生缓存生成器**」。
> 两者的工作性质完全不同：
>
> | | 原以为 | 实际 |
> |---|---|---|
> | 性质 | 写适配器解析 `.3DR` | 由既有要素**算出**逐桩 κ(s)/G(s)/E(s) |
> | 输入 | 一个尚未生成的文件 | `alignment_element`(33) + `station_sequence`(332) 等**已入库** |
> | 阻塞 | 需向外部索取 `.3DR` | **无外部阻塞** —— 全部输入在手 |
> | 验收 | 能解析出东西 | **可重建**：重算 ≡ 已存，且同批次 |
>
> **好消息**：既然它是派生量，本 spec 反而**不被 `.3DR` 缺失阻塞** ——
> 所需的要素与桩号**都已入库**，可以直接算。
> **坏消息**：初稿把它当「适配器缺口」，方向错了，
> 这也解释了为什么 feature 001 把它归为 `source_absent` 而我一直当作待写适配器。

**范围修正（2026-09-27）**：`alignment_element`（33 行）与 `station_sequence`（332 行）
**均已入库**，缺的是二者之间的**求值器**。详见「背景二」与 FR-012~018 状态表。

## 背景：为什么必须先动桩号

用户提出一个结构性观察，**实测证实了它**：

| 路段 | 桩号区间（km） | 桩号序列行数 |
|---|---|---|
| 1 滨海大通道试验段 | **4635.000 ~ 4654.701** | **0** |
| 6 毕设 | **0.000 ~ 5.805421** | **332** |

两个路段相差 **4635 km**，不可能共享同一个「全线桩号基准」；而当前 332 个桩号**全部只挂在 section 6 之下**，section 1 一个都没有。

现行外键方向把「客观基准」塞进了「局部划分」：

```
station_sequence.section_id  ->  road_section   （桩号挂在路段下）
road_section.line_id         ->  road_line
```

三个问题随之而来：

1. **路段不确定**：路段是管理划分，会调整；桩号是客观里程，不会变。把不变的挂在会变的下，是层次倒置。
2. **路段长度不定**：`road_section.length_m` 实测 19701.0 与 5805.4，但路段边界由人填（`start_station_text` 是文本），无约束。
3. **路段之并不覆盖整条路线**（用户明确指出）：桩号区间的**并集是全集**，路段的并集**允许有洞**。用路段去界定桩号，会丢掉洞里的桩号。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 桩号脱离路段独立存在 (Priority: P1)

数据管理员导入 `.STA` 桩号序列文件时，桩号锚定在**路线/设计项目**上，而不是锚定在某个路段下。路段的建立、调整、删除都不影响已导入的桩号。

**Why this priority**: 这是本 spec 的根。桩号是全部设计文件的公共坐标，`geometry_point`、横断面、土方、超高、路幅全部以它为锚。锚错了，上层全错 —— 而错误会以「行数对但桩号错位」的形式静默传播。

**Independent Test**: 让 `station_sequence.section_id` 可以为空；导入 `.STA` 后，即使没有任何 `road_section` 记录，332 个桩号仍然完整存在。

**Acceptance Scenarios**:

1. **Given** 库中不存在任何 `road_section`，**When** 导入 `.STA`（332 个桩号），**Then** 332 个桩号全部入库，且各自的路线归属正确可查。
2. **Given** 已导入 332 个桩号且挂在某路段下，**When** 该路段被调整（改名/改边界），**Then** 桩号不受影响（不改动、不被级联删除）。
3. **Given** 两个路段桩号区间相差 4635 km，**When** 查询「全路线桩号」，**Then** 能按路线分别返回各自的桩号集合，不混淆。

### User Story 2 - 文件覆盖区间被记录，越界即报错 (Priority: P1)

导入任何设计文件时，系统记录该文件的**桩号覆盖区间**，并校验它是否落在其声明的范围内。越界**报错并拒绝入库**，不静默丢弃。

**Why this priority**: 实测已发现真实的越界风险 —— `.STA` 到 **K5+805.421**，而 `.WID`（路幅宽度）只到 **K5+701.461**，**短 103.96 m**。若不校验，`geometry_point` 的最后 104 米会凭空生成或静默丢失，而两种结果都不会报错。

**Independent Test**: 导入一个覆盖区间超出声明范围的文件，导入必须失败并给出越界的具体桩号与差值。

**Acceptance Scenarios**:

1. **Given** `design_file` 记录了某文件的覆盖区间，**When** 导入该文件，**Then** 实际解析出的桩号区间与记录区间一致，否则导入失败。
2. **Given** 某文件的实际覆盖短于其声明（如 `.WID` 短 103.96 m），**When** 导入，**Then** 系统明确报出缺失区间与长度，不静默补值。
3. **Given** 一次导入失败，**When** 查看结果，**Then** 库中没有该文件的任何部分数据。

---

### User Story 3 - 桩号文本与数值可互相还原 (Priority: P1)

每条桩号记录的**文本形式**（`K0+020.000`）与**数值形式**（`0.020` km）必须能互相解析还原。任一条记录不一致即为错误。

**Why this priority**: 两列独立存储、无约束（实测 332 行恰好全部相等，但那是因为数据干净，不是因为机制保证）。桩号一旦错位，所有按桩号对齐的操作都会得到看似合理但错误的结果。

**Independent Test**: 构造一条 `station_text` 与 `station_local_km` 不符的记录，校验必须拒绝它。

**Acceptance Scenarios**:

1. **Given** 一条桩号记录，**When** 校验，**Then** 文本解析出的数值等于数值列。
2. **Given** 一条文本与数值冲突的记录，**When** 导入，**Then** 导入失败并指出该行。

### User Story 4 - 逐桩线形作为**可重建的派生缓存** (Priority: P2)

线形数据以**分段要素**的形式入库：直线段、缓和曲线段、圆曲线段各自带参数（A 值、半径 R、起讫桩号）。
`station_interval_m`（20 m）下生成的 332 个采样点，是这些要素的**一个视图**，可由要素**重算**得到。

**Why this priority**: 这是本 spec 的产出目标，也是 TruckSim / FEM 的公共输入。排在 P2 是因为**它的正确性完全依赖 P1 的桩号基准** —— 桩号错了，算出来的要素再精确也是错的。

**它是什么**：`geometry_point` **不是**独立数据源，而是**派生缓存** ——
由 `alignment_element`(33) 与桩号等**已入库**输入逐桩算出。
契约已规定它存得有理由（缓和曲线要数值积分，逐桩重算代价高），
但**必须可重建**且**与要素同批次**。

**为什么不是「生成 332 行」**：实测 `.PM` 含 **33 个带完整参数的线形单元**（见「背景二」）。
若只存 332 个采样值，曲率 κ 会被**折线化** —— 折点处 κ 跳变，
整车动力学仿真会因此产生**实际不存在的冲击响应**。存要素则不会：消费方按自己的步长求值，κ 连续。

**Independent Test**: 解析 `.PM` 得 33 个要素单元，其长度合计等于 `.STA` 的末桩号；
再由要素重算 332 个采样点，与 `.STA` 桩号逐行对齐。

**Acceptance Scenarios**:

1. **Given** `.PM` 就位，**When** 解析，**Then** 得 **33 个要素单元**，
   单元长度合计 **5805.421 m**，与 `.STA` 末桩号一致（误差 < 1 mm）。
2. **Given** 要素已入库，**When** 按 `station_interval_m` 重采样，**Then** 得 **332 个采样点**，
   与 `station_sequence` 一一对应（无多、无少、无错位）。
3. **Given** 某要素单元的 A 值与 R 已解析，**When** 与 `.JD` 交叉核对，
   **Then** 曲线总长一致（实测锚点：第 1 交点 **674.493 m**）。
4. **Given** 某桩号在源文件中无数据（如 `.WID` 覆盖不到的最后 103.96 m），
   **When** 取值，**Then** 该字段为 NULL 并附说明，不得填 0 或外推。

| 第 3 行 | 6 | 起点记录：1 / 0.0000 / 起始方位角(rad) / ? / X / Y |

### 实测解码结果

```
解析出 33 个线形单元
单元长度合计: 5805.421 m        <- 与 .STA 末桩号一致
曲线单元 16 个 / 直线单元 17 个
要素码分布: 1×9  21×8  3×8  22×8
```

每 4 个单元构成一个完整平曲线。示例（第 2 个交点）：

```
单元  5  虚线  718.682 ~ 1393.176  (674.493 m)  A1=674.493  第一缓和
单元  6  虚线 1393.176 ~ 1463.176  ( 70.000 m)  R=450       圆曲线
单元  7  虚线 1463.176 ~ 1589.917  (126.742 m)  R=450       圆曲线
单元  8  虚线 1589.917 ~ 1659.917  ( 70.000 m)  R=450       第二缓和
```

### 独立交叉验证（验收锚点）

用 `.JD`（平面交点）作第二来源核对：

| 来源 | 值 |
|---|---|
| `.PM` 单元 5 长度 | **674.493 m** |
| `.JD` 第 1 交点曲线总长 | **674.493 m** |
| `.JD` 半径 R | 450.000 |
| `.PM` 圆弧段 R | 450.000 |

**两者完全吻合** —— 解码正确，非巧合。此锚点 MUST 进入契约测试。

### 曲率 κ 是分段函数

```
直线段      κ = 0
缓和曲线段   κ = s / A²     <- 线性变化，这正是缓和曲线的定义
圆曲线段     κ = 1 / R      <- 常数
```

**存要素 → κ 连续；存 332 个采样值 → κ 在折点跳变。**
这是选择方案 B 的**工程理由**，不是偏好。

---
### Edge Cases

- **路段与桩号无交集**：路段 1 声明 K4635~K4654，桩号在 K0~K5.8，二者无交集。系统不得因此报错或强行关联，应如实报告「无交集」。
- **断链尚未发生**：实测 `station_equation` 为 0 行，故 `station_local_km` 与 `station_absolute_km` 恒等（332/332）。两列是**为断链预留**的，当前冗余是**正确**的，不得据此删除其一。
- **同一桩号出现两次**：断链点前后可能重号。系统须能承载，不得用唯一约束误杀。
- **空桩号文件**：`.STA` 解析出 0 个桩号时，须报错，不得当作「成功导入 0 行」。
- **桩号类型**：实测 290 整桩 + 40 加桩 + 2 端点 = 332。加桩（非整数米）不得被规整到整桩。

## Requirements *(mandatory)*

### Functional Requirements

#### 桩号基准（P1）

- **FR-001**: 系统 MUST 允许桩号序列**独立于路段**存在 —— `station_sequence.section_id` 必须**可为空**，且桩号的路线归属可另行表达。
- **FR-002**: 系统 MUST 保证路段的新增/修改/删除**不影响**已导入的桩号；删除路段 MUST NOT 级联删除桩号。
- **FR-003**: 系统 MUST 能按**路线**分别查询桩号集合，使桩号区间相差数千公里的两条路线互不混淆。
- **FR-004**: 系统 MUST NOT 假定「路段之并等于路线全桩号」；桩号集合的完备性 MUST 以桩号文件自身为准，不以路段覆盖为界。

#### 覆盖区间校验（P1）

- **FR-005**: 导入任一设计文件时，系统 MUST 记录该文件实际解析出的桩号覆盖区间（起、止），写入 `design_file.coverage_from_station_km` / `coverage_to_station_km`。
- **FR-006**: 当文件的实际覆盖区间与其声明区间不符时，系统 MUST 导入失败，并报出：文件、声明区间、实际区间、差值（米）。
- **FR-007**: 导入失败时，该文件 MUST NOT 有任何部分数据入库（原子性）。
- **FR-008**: 系统 MUST NOT 对缺失区间做任何补值、外推或默认填充。

#### 桩号一致性（P1）

- **FR-009**: 每条桩号记录的文本形式与数值形式 MUST 可互相解析还原；不一致时导入失败并指出具体行。
- **FR-010**: 桩号校验 MUST 覆盖**全部**记录，不得只抽样；且 MUST 有一条元测试证明「坏数据会被拒绝」。
- **FR-011**: 系统 MUST 保留桩号类型（整桩/加桩/端点），加桩 MUST NOT 被规整。

#### 线形要素（P2）

- **FR-012**: 系统 MUST 解析 `.PM` 的线形单元，取出**类型码、A1/A2、R、起讫桩号、方位角**；
  实测应得 **33 个单元**，长度合计 **5805.421 m**。
- **FR-013**: 系统 MUST 保留**要素码**（`1` 直线 / `21` 第一缓和 / `3` 圆曲线 / `22` 第二缓和），
  MUST NOT 把缓和曲线段与圆曲线段混为一类 —— 二者的 κ 表达式不同。
- **FR-014**: 系统 MUST 由要素**重采样**出 `station_interval_m` 下的采样点；
  采样密度 MUST 可配置，MUST NOT 把 20 m / 332 点烧死进数据。
- **FR-015**: 系统 MUST NOT 只存采样值而不存要素 ——
  否则 κ 被折线化，消费方会算出实际不存在的冲击响应。
- **FR-016**: 解析结果 MUST 与 `.JD` 交叉核对；不一致时 MUST 报错。
  验收锚点：第 1 交点曲线总长 **674.493 m**。
- **FR-017**: 要素的每一行 MUST 可追溯到其源文件；
  源数据缺失时 MUST 为 NULL 并附原因，MUST NOT 填 0 或外推。
- **FR-018**: 要素与采样 MUST 可按桩号区间查询，供 Chrono / FEM 消费。
  （2026-10-09 口径更新：原写「TruckSim / FEM」。经

#### ★ `geometry_point` 的两条硬性验收（来自既有契约，非本 spec 新立）

`contracts/design-import/README.md` 第 437–439 行已写明它是**合理的缓存**，
但必须满足两条 —— **本 spec MUST 原样继承，不得放宽**：

1. **可重建**：导入器能一键重算，并**断言重算结果 ≡ 已存结果**
2. **同批次**：与 A12（`alignment_element`）**同批次生成**

并且（第 427 行）：`geometry_point` 由 **A12 + A13/A14 逐桩算出**。
即：**这不是独立数据源，是派生缓存。**

### 因此本 spec 的真实工作量（修正）

`geometry_point` **不是**「从零解析 `.PM` 再算线形」，而是：

> **把已入库的 `alignment_element`（33 行要素）与 `station_sequence`（332 行桩号）求值联结，**
> **产出 332 行逐桩线形。**

输入两侧**都已就位**，缺的是**它们之间的求值器**。这比原估计小得多，也更聚焦。

**规划 MUST 以此为准，不得重复实现既有解析器。**

### Key Entities

- **桩号 (station)**: 路线上的一个客观里程位置。关键属性：数值桩号、文本桩号、桩号类型（整桩/加桩/端点）。**独立于路段存在**，是全部线形数据的公共坐标。
- **桩号体系 (station system)**: 一条路线上全部桩号的集合，含断链定义。完备性由桩号文件决定，不由路段划分决定。
- **路段 (road section)**: 路线的**管理划分**，是对桩号区间的一种标定。允许有洞、允许调整、长度不定。**不得**反过来界定桩号。
- **文件覆盖区间 (file coverage)**: 某个设计文件实际覆盖的桩号范围。不同文件的覆盖区间**可以不同**（实测 `.STA` 与 `.WID` 相差 103.96 m），此差异必须被记录而非被抹平。
- **线形要素 (alignment element)**: 线形的一段**解析定义**：直线 / 缓和曲线 / 圆曲线，带 A 值、半径 R、起讫桩号、方位角。**这是保真层** —— κ 在其上是连续的分段函数。实测 `.PM` 含 33 个。
- **线形采样点 (geometry sample)**: 在 `station_interval_m` 网格上对要素**求值**得到的点。**这是视图层，可重算** —— 不是原始数据。实测 332 个。
- **要素码 (element code)**: 纬地对线形段的分类：`1` 直线 · `21` 第一缓和 · `3` 圆曲线 · `22` 第二缓和。决定 κ 用哪个表达式。

## Assumptions

- **桩号锚定到路线而非设计项目**：因为实测设计项目只有 1 条，而路线有 5 条，桩号属于「路线」这个更稳定的层级。此假设如需变更，属架构决策，走工单。
- **`.STA` 是桩号基准的真源**：`.PRJ` 与其一致（均 0.000~5805.421），`.WID` 短 103.96 m 属被校验方而非基准方。
- **断链表当前为空是正常状态**：实测 `station_equation` 0 行，故 local 与 absolute 恒等；这不是缺陷，是断链尚未发生。
- **332 是采样数，不是基准**：用户确认「采样」。`design_project.station_interval_m = 20.00` 是采样规则，
  332 = 291 个 20 m 格点 + 40 个加桩 + 2 个端点，是**产物**而非原始数据。
- **`.PM` 是线形要素的真源**：其 33 个单元长度合计 5805.421 m，与 `.STA` 一致，且能与 `.JD` 交叉验证。
- **`.PM` 每个完整交点固定 4 段**：直线 → 第一缓和(21) → 圆(3) → 第二缓和(22)。
  实测 33 = 9 直线 + 8×3 曲线段，对应 8 个完整交点与若干纯直线段。
