# 路线线形能否以 0.1 m 纵向分辨率生成 Chrono 路面（OpenCRG）—— 数值验证

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-30 |
| 结论 | ✅ **可以**。33 段线形全部可用解析式重建，0.1 m 采样全路线 **58,054 点** |
| 验证对象 | `alignment_element` 33 行（路段全长 5,805.421 m） |
| 数据来源 | PostgreSQL `road_pavement`（容器 `rp-pg`），**库中真实数据，非插值** |
| 关联文档 | `评估-Chrono替代TruckSim.md` §4 第 1 步「打通」；本验证即该步的可行性前提 |

---

## 0. 结论先行

**「0.1 间隔可以做吗」——可以，且不需要任何新数据。**

用库里 33 行 `alignment_element`（9 直线 + 16 缓和曲线 + 8 圆曲线）逐段解析积分，
全路线重建的最大终点残差为 **6.92e-04 m**（亚毫米级），
远小于 0.1 m 采样间距（约为其 **1/140**）。

**关键结论：线形是解析可积的，不存在「必须内插才能细分」的问题。**
0.1 m 采样点由解析式直接算出，不是从更粗的点列插值出来的。

## 1. 采样点数

| 量 | 值 |
|---|---|
| 路线全长 | 5,805.421 m（5.805421 km） |
| 采样间距 | 0.1 m |
| **逐段取整求和（+1 末尾端点）** | **58,054 点** |
| 对照：全长/0.1 + 1（不做逐段取整） | 58,055 点 |

★ 两个口径差 1 点，来源是**逐段取整**：各段长度并非 0.1 的整数倍，
逐段 `round(L/0.1)` 会把每段的零头截掉，累计少 1 点。

**实施建议**：以**全路线连续里程**为采样轴（0, 0.1, 0.2 … 5805.4, 5805.421），
得到 58,055 点，段边界自然落在采样点上，不产生接缝。
若按段生成再拼接，需要显式处理段边界的重复点，否则 CRG 的 u 轴会出现 0.1 m 的平台。

## 2. ★ 必须先说清的一个坑：缓和曲线的曲率模型

这是本次验证**最重要的一条发现**，写错会让整条线形偏掉数米。

### 2.1 库中半径列没有方向，且**只填一端**

`alignment_element` 的 `radius_start_m` / `radius_end_m` **无符号**，
并且**入口缓和曲线只填 `radius_end_m`，出口缓和曲线只填 `radius_start_m`**（另一端为 NULL = ∞）。

| 段型 | `radius_start_m` | `radius_end_m` | 含义 |
|---|---|---|---|
| 入口缓和 | NULL | R | κ 由 0 线性增到 1/R |
| 出口缓和 | R | NULL | κ 由 1/R 线性减到 0 |
| 圆曲线 | R | R | κ 恒为 1/R |
| 直线 | NULL | NULL | κ = 0 |

**曲率方向必须由 Δazimuth 反推，不能由半径列读出。**
用 `radius_start_m` 是否为 NULL 即可**唯一判定**入口/出口 —— 实测 16 段全部命中。

### 2.2 缓和的转角关系是 Δaz = L/(2R)，不是 L/R

实测 16 段缓和曲线**全部**满足：

```
Δaz = L / (2R)        （κ 由 0 线性变到 1/R 的积分结果）
```

若误用 `Δaz = L/R`，转角会**翻倍**，线形立刻歪掉。
这一条已逐段核验（16/16 命中，误差 < 1e-6°）。

### 2.3 若用「方位角线性」近似会怎样

一个看似合理的近似是「段内方位角线性插值」。
对**缓和曲线这不成立**（真实回旋线的 az 是 s 的**二次**函数，κ 才线性）。

实测后果：

| 模型 | 缓和曲线最大残差 |
|---|---|
| 方位角线性插值 | **2.31 m** ❌ |
| κ 线性（真回旋线） | **3.03e-06 m** ✅ |

**2.31 m 的误差不会随步长缩小** —— 它是模型误差，不是精度误差。
这与「半径符号」那个坑是同一类：**看起来像数据不精，实为公式用错。**

## 3. 逐段重建残差（0.1 m 解析积分 vs 库中记录终点）

| 段型 | 段数 | 最大残差 | 评价 |
|---|---|---|---|
| `line` | 9 | 6.39e-04 m | 亚毫米 |
| `transition` | 16 | **3.03e-06 m** | 微米级，近乎精确 |
| `circular` | 8 | 6.92e-04 m | 亚毫米 |
| **全局** | **33** | **6.92e-04 m** | ✅ |

### 残差来源已定位

直线段的端点残差与段长成正比（残差/L ≈ 1e-06），
且**方位角本身**表列值与几何反算值只差 ~2e-07°（纯 6 位小数取整）。

**结论：残差来自 `start_x/start_y/end_x/end_y` 坐标列的存储与里程列之间 ~1e-06 的尺度差，
不是线形模型错误。** 亚毫米量级，对 0.1 m 采样完全无影响。

## 4. 对「生成 Chrono 路面」的直接含义

| 项 | 结论 |
|---|---|
| 纵向分辨率 0.1 m | ✅ 可做，58,055 点（全路线连续里程口径） |
| 是否需要插值 | ❌ 不需要，解析式直接给点 |
| 是否需要新数据 | ❌ 不需要，只用现有 33 行 |
| 垂向（高程/坡度） | 另有 `profile_grade_point` 12 行，同为解析数据，可同法处理 |
| 横向（做三维路面） | `cross_section_ground_point` 2215 行，但**注意**：它是地面线 `.HDM`，不是路面（见评估文档） |
| 摩擦系数 | ❌ 库里没有，需按评估 §2.2 决策（建议分路段常数起步） |

### 与 OpenCRG 对接的注意点

- CRG 的 `REFERENCE_LINE_INCREMENT` 填 **0.1**，`u` 轴从 0 到 5805.421。
- 本验证已用独立脚本按 **OpenCRG 2.0.1 §6.4** 的硬性规则逐条校验过一个试生成文件
  （头行 ≤72 字节纯 ASCII、`$ROAD_CRG`/`$KD_DEFINITION` 段齐备、
  `REFERENCE_LINE_INCREMENT` 存在、通道数 == 数据列数、
  v 单调且间隔恒定、数据全数值、u 行数与 `(U1-U0)/UINC+1` 相符）。
  **该试生成件仅为格式自测，不是交付物**（200 m × ±5 m 的样例）。

## 5. 复现方法

数据经容器内 `psql` 直接读出，逐段解析积分（不依赖任何仓库脚本）：

```sql
SELECT element_seq, element_type, start_station_km, end_station_km,
       azimuth_deg, end_azimuth_deg, radius_start_m, radius_end_m,
       start_x, start_y, end_x, end_y
FROM alignment_element ORDER BY element_seq;
```

积分式（段内，s 自段首起算，κ 线性）：

```
κ(s) = k0 + (k1 - k0) · s / L
az(s) = az0 + k0·s + (k1 - k0)·s² / (2L)
x(s) = x0 + ∫ cos(az) ds ,  y(s) = y0 + ∫ sin(az) ds
```

其中 `(k0,k1)` 由 §2.1 的表按段型与 NULL 模式确定，符号由 Δazimuth 给出。
