## 0. 摘要（给导师的一页）

**问题**：桩号现在挂在**路段**下。路段是被设计出来的、会变的；桩号是野外客观存在的、不变的。
把不变的挂在可变的下面，就会「删一个路段，桩号跟着没了」。

**证据**（实库实测，非推断）：

| 事实 | 实测值 |
|---|---|
| `station_sequence.section_id` | `bigint NOT NULL`，外键指向 `road_section` |
| 引 `road_section` 的子表 | **30 张**（不含 `station_sequence` 自身）——即删一个路段会牵动半个库 |
| 引 `station_sequence` 的子表 | **4 张**（`geometry_point` / `profile_ground_point` / `roadbed_design_point` / `earthwork_section`） |
| 毕设路段桩号 | 332 个，全部挂在 `section_id=6` 下 |
| **既有唯一约束** | `UNIQUE (section_id, station_local_km)` —— **改可空后会对 `NULL` 行静默失效**（§3.3） |

**改法**：`section_id` 改为**可空**，桩号改为锚定**路线**（`road_line`），
路段降级为「对桩号的**引用**」而不是「桩号的**容器**」。

**为什么必须现在决定**：本工单是 feature 002 的 US1。US4（逐桩线形）已完成，
它**只读** `station_sequence`，所以与甲方案结构上独立 —— 这个决定没有被 US4 预先绑定，
越晚改，下游依赖 332 条桩号的模块越多，迁移成本越高。

## 1. 为什么要走这张工单

### 1.1 概念的层级关系：桩号是基础，路段是派生

导师已明确的判断：

> 「需要，桩号是基础，客观存在的……路段长度不定，另外不是所有路段加起来可以覆盖整条路线桩号。」

这句话同时否掉两件事：

1. **路段不能当桩号的容器**——路段长度不定，桩号的取值范围不取决于它；
2. **路段之并 ≠ 路线全桩号**——存在无路段覆盖的桩号（对应 FR-004）。

所以正确的层级是：

```
路线 road_line          ← 桩号的锚（一条设计项目只有一条路线）
   └── 桩号 station_sequence   ← 客观基准，完整、连续
         ↑ 被引用（可空）
      路段 road_section    ← 设计产物，覆盖部分桩号，可有洞
```

注意箭头的方向变了：现在路段是**父**，改完桩号是**基础**、路段是**引用它的那个**。

### 1.2 现在这个方向会怎么坏

`station_sequence.section_id` 是 `NOT NULL` + 外键。于是：

| 操作 | 现在的后果 |
|---|---|
| 删除一个路段 | 要么被 30 张子表挡住删不掉，要么级联删掉 332 个桩号 |
| 路段边界调整 | 桩号被迫重新归属，`design_import_batch` 的血缘随之失效 |
| 导入一条新路线的桩号 | 必须先造一个假路段才能装下桩号 —— 而桩号**并不属于任何路段** |

最后一条是当下最现实的：`station_sequence.station_local_km` 是**相对该路段起点**的
（毕设 0→5805.421）。桩号本身不需要路段就成立，是现在的表结构硬把它绑上去的。

## 3. 变更内容

### 3.1 DDL 改动（三处，全部是「放宽」或「新增」）

| # | 改动 | 性质 |
|---|---|---|
| 1 | `station_sequence.section_id` → **改可空**（`DROP NOT NULL`） | 放宽 |
| 2 | `station_sequence` 新增 `line_id bigint REFERENCES road_line(id)` | 新增（可空） |
| 3 | `station_sequence.section_id` 的 FK 加 `ON DELETE SET NULL` | 放宽 |
| 4 | **（待裁决，见 §3.3 Q1）** 补部分唯一索引 `UNIQUE (line_id, station_local_km) WHERE line_id IS NOT NULL` | **收紧** ← 本工单唯一一处 |

**没有**删列、**没有**收紧约束、**没有**改类型。见 §5。

### 3.2 为什么 `line_id` 可空而不是 `NOT NULL`

已有数据的 `section_id` 可以反推出 `line_id`（`station_sequence → road_section.line_id`），
理论上能一次填满。但**仍然保持可空**，理由：

- 桩号在**导入那一刻**可能还不知道属于哪条路线（先有 `.STA` 文件，后有路线建档）；
- 强制 `NOT NULL` 会让「先导桩号、后建路线」这个合法顺序变得不可能；
- 可空 + 后续 `UPDATE` 回填，比 `NOT NULL` + 先造占位路线**诚实**。

### 3.3 既有唯一约束会被本工单「打漏」—— ★ 请导师重点裁决

**实库实测，现状已有一条唯一约束**（这一点**推翻**了起草时的初判「无 UNIQUE 约束」）：

```
station_sequence_section_id_station_local_km_key
  UNIQUE (section_id, station_local_km)
```

它现在的含义是：**同一个路段内，桩号数值不重复**。在「桩号必属某路段」的世界里，这已经够了。

但本工单把 `section_id` 改成**可空**之后，这条约束会**静默失效一部分** ——
因为 PostgreSQL（以及 SQL 标准）中 `NULL` 在 `UNIQUE` 里彼此**不相等**：

```sql
-- 以下三条在 PG 里全部合法，不会违反 UNIQUE (section_id, station_local_km)
INSERT INTO station_sequence (section_id, station_local_km) VALUES (NULL, 0.000);
INSERT INTO station_sequence (section_id, station_local_km) VALUES (NULL, 0.000);
INSERT INTO station_sequence (section_id, station_local_km) VALUES (NULL, 0.000);
```

这**不是理论风险**：受影响的正是本工单要支持的新场景 ——
「路段未定」（`section_id IS NULL`）的桩号。它们可以无限重复而不报错。

> 这是本工单最需要导师注意的一处：**一条保护了整张表的约束，会因为改一个可空性而出现缺口。**

**候选方案：**

| 方案 | 约束 | 优点 | 代价 |
|---|---|---|---|
| **A（建议）** | 补 `UNIQUE (line_id, station_local_km) WHERE line_id IS NOT NULL`（**部分唯一索引**） | 把「唯一」的锚从**路段**移到**路线**，与新层级一致；`line_id` 非空的行仍受完整保护 | `line_id` 也为空的行仍不受保护（但那正是「还不知道属于谁」的桩号，本就无法判重） |
| B | 把既有约束改成 `UNIQUE (line_id, station_local_km)`，不保留 `section_id` 版 | 更彻底 | 既存数据需先回填 `line_id`，否则约束建不上 |
| C | 不动 | 改动最小 | 留下 §3.3 描述的缺口，且**没有任何测试会发现它** |

**我的建议：A。** 理由：A 不要求先回填数据（`WHERE` 子句让约束只作用在已锚定的行上），
可增量推进；而且它把唯一性的**层级**改对了 —— 桩号的唯一性本来就该由**路线**定义，不该由路段定义。

**但这一条超出「只改可空性 + 加一列」的范围，请导师明确是否一并纳入本工单**，还是留到后续版本。

> ★ **无论选哪个，T023 的测试都必须包含一条「唯一约束的元测试」**：
> 尝试插入两条 `(NULL, 0.000)`，断言**当前行为**符合所选方案 ——
> 否则这个缺口会一直存在且无人知晓。

## 5. 兼容性声明

**不破坏兼容。** 逐条说明：

| 变更 | 旧读法是否仍有效 |
|---|---|
| `section_id` 改可空 | ✅ 有效。原来非空的行仍然能读到非空值 |
| 新增 `line_id` | ✅ 有效。旧查询不引用它即可 |
| FK 加 `ON DELETE SET NULL` | ⚠️ **语义变化**：原先删路段要么失败要么级联删桩号，现在会保留桩号并把 `section_id` 置空。**这是本工单的目的**（FR-002） |

第二条需要导师注意的：若采纳 Q1，**新增了一个部分唯一索引** ——
它只作用于 `line_id IS NOT NULL` 的行，不影响任何既存数据；
但若将来回填 `line_id` 时发现同路线内有重复桩号，`CREATE INDEX` 会失败。
**这是好事**：它把原本静默的重复变成了一次显式的建索引失败。

唯一需要下游注意的一条：**`section_id` 现在可能是 `NULL`**。
所有「按路段查桩号」的既有查询，若要覆盖「hasn't been assigned to a section yet」的桩号，
需要显式处理 `NULL`。**但反过来说：如果不改，这些桩号根本不可能存在。**

## 6. 回滚方式

1. **DDL**：反向 migration（`ADD NOT NULL` 需先回填 `section_id`，故回滚脚本里**必须先补数据**再收紧约束 —— 见下）；
2. **代码**：`git revert <本工单提交>`；
3. **数据**：本工单不改任何既存行的值，回滚无需数据迁移。

★ 回滚的**唯一陷阱**：若此时已产生 `section_id IS NULL` 的行，
反向 `SET NOT NULL` 会失败。因此回滚脚本 MUST 先检查并处理这些行，
而不是直接 `ALTER TABLE ... SET NOT NULL`（那样会在生产库上炸）。

## 7. 验收标准

| # | 标准 | 验证方式 |
|---|---|---|
| 1 | 删除一个路段后，桩号**仍在** | 契约测试：删路段 → `count(*)` 不变（FR-002） |
| 2 | 被删路段下的桩号 `section_id` 变为 `NULL` | 同上，断言 `IS NULL` |
| 3 | 两条路线的桩号互不混淆 | 造两条 `line_id` 不同的桩号，按路线查询各得其集合（FR-003） |
| 4 | DDL(fresh) == DDL + migrations | 既有 `m1-装库一致` 契约测试 |
| 5 | 全部既有契约测试仍绿 | `./run_contract_tests.sh` → 14/14 |

★ 验收 1 是本工单的**核心**，也是最容易做成空转的一条：
如果测试用的路段本来就没有桩号，那「删完桩号还在」当然成立。
测试 MUST 先断言「删之前该路段**确实有**桩号」，再删、再断言 ——
否则就是宪法原则 V 说的「一个永远不会失败的检查」。
