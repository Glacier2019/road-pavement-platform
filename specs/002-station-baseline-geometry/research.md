## 问题 1：缓和曲线数值积分法 —— ✅ **已解决，无需研究**

### 现状

`scaffold/modules/M2-ingest/adapters/geom.py` **已实现完整的逐桩求值**：

| 函数 | 作用 |
|---|---|
| `curvature_at(element, s)` | 曲率 κ(s)；含转向符号 |
| `azimuth_at(element, s)` | 方位角 θ(s) —— **闭式精确**，非数值 |
| `point_at(element, s)` | 坐标 (x,y) —— 复合 Simpson |
| `locate(elements, s)` | 桩号落在哪个单元；**落外返回 None，不外推** |

### 关键技术判断（代码中已记载，且与我的判断一致）

**方位角无需数值积分**：曲率线性 ⇒ `∫κ ds` 是二次式，闭式精确：

```
Δθ = κ₀·d + (κ₁ − κ₀)·d² / (2L)
```

**只有坐标需要积分**：`∫(cosθ, sinθ) ds`。直线与圆曲线本有闭式，
但缓和曲线（回旋线）要 Fresnel 积分、**无初等闭式**，故统一走复合 Simpson
—— 一条路，误差可控（`steps=64` 时实测 < 1e-9 m）。

### 判据已通过（本次实测，真实 33 单元）

判据来源是**源文件自带的** `end_x`/`end_y`/`end_azimuth_deg` —— 纬地自己算的，
独立于本模块公式。用 `point_at(el, end_station)` 与它们对质：

```
最大坐标偏差  : 3.171e-08 m
最大方位角偏差: 1.589e-09 deg
```

**远优于 plan 中定的 < 1e-6 m 判据**（实际好 30 倍以上）。

### 逐桩可行性已验证

拿实库 332 个真实桩号逐一代入 `locate` + 三个求值函数：

```
可求值: 332   无法定位: 0
```

**332/332 全部落在单元链内，没有一个需要外推。**

### ⚠ 代码中记载的两个陷阱（我若自己写会踩）

1. **`radius_start_m = None` 是「无穷大半径」（κ=0），不是缺值**。
   缓和曲线起点正是这种情况：R 从 ∞ 渐变到 R。
2. **曲率符号来自 `turn_flag`**（+1 左转 / −1 右转）；`radius_*_m` 恒为正。
   代码原文：「漏掉转向，右转的曲线会朝反方向弯 —— **实测终点差 98 m，而且不报错**」。

**结论：问题 1 不再需要研究。直接复用 `geom.py`。**

## 问题 2：`.SUP` 超高插值 —— ✅ **已解决，且有明确的 NULL 语义**

### 现状

`superelev_transition` 表已存在，**本工程 76 个过渡变化点**。
DDL 注释已定义清楚：

> 一行一个过渡变化点。六列横坡绕桩号左右对称；
> **NULL 表示源文件写了 9999「可以忽略此数据」，即该列在此位置不参与约束、
> 过渡照常继续（不是缺值、也不是沿用上值）**。

### ★ 一个必须遵守的实测约束

DDL 第 610–614 行原文：

> **不挂 `station_id` 外键**，与 A16 同理，且已用实库数据验证过：
> **.SUP 的 76 个变化点里只有 34 个落在 `station_sequence` 里**，
> `.WID` 的 5701.461 也不在。**设计变化点的桩号本来就不是 `.STA` 那个桩号序列** ——
> 硬挂外键就得先往 `station_sequence` 里塞"不是桩号序列的点"，那是污染一等实体。

**这直接证实并量化了用户的核心观察**：「路段之并不覆盖整条路线」「桩号是采样」。
76 个设计变化点里 **42 个不在桩号序列中** —— 若强行走外键，必然丢数据。

### 对 `geometry_point` 的含义

`geometry_point` 的六列横坡要**插值到逐桩**（在 332 个桩号上取值），
而插值源 `superelev_transition` **按桩号点查即可**（有 `idx_superelev_trans_station` 索引）。

**待定（留给 Phase 1）**：线性还是曲线过渡？
—— 但注意：`.SUP` 存的是**变化点本身**，两点之间如何过渡取决于设计；
需要核对 `.SUP` 是否含过渡形式字段。**若不含，则线性插值并注明**，不臆造。

## ★★ 问题 5（实现中新增发现）：桩号精度在库中只有 1 mm，而 .PM 有 8 位小数

这一条**不在原研究计划里**，是 MVP 实现（T004–T005）跑通端到端时暴露的。

### 现象

用 `geom.point_at` 求末点坐标，与源文件自带的 `end_x`/`end_y` 对比：

```
.per-element 精度（在 .PM 自己的桩号上求值）：最大偏差 3.171e-08 m   OK
但用**库里的末桩号 5805.421** 求值        ：偏差 3.685e-04 m   BAD
```

同一套公式，**差了四个数量级**。

### 根因：两处桩号的小数位不同

| 来源 | 值 | 小数位 |
|---|---|---|
| `.PM` 单元末端桩号 | `5805.42136846` | **8 位** |
| 库 `station_local_km`（`numeric(12,6)`） | `5805.421000` | **6 位** |
| 差 | `0.00036846 m` = **0.37 mm** | |

实测统计（34 个去重单元端点）：

```
精确落在库桩号上的: 1 / 34
最大距离          : 0.000464 m = 0.46 mm
```

**34 个单元端点里只有 1 个能被库桩号精确表示。**

### 这是**已记录问题之外**的新问题

契约 README 第 328–340 行已记录过一次桩号精度问题：
`numeric(10,3)` → `numeric(12,6)`，解决的是**碰撞**（0.083 m 间距的两个桩号
在 km 3 位小数下撞 UNIQUE）。那次修的是「**装不下两个相邻点**」。

**本次不是同一件事**：现在不碰撞了，但**分辨率仍不足以表示 `.PM` 端点的真实值**。
README 原文那句「预留了字段，没预留分辨率」在这里**再次成立**，
只是这次的对象是 `.PM` 的 8 位小数，而不是 `.STA` 的加桩间距。

### 影响评估

| 项 | 是否受影响 |
|---|---|
| `geometry_point` 行数 = 332 | 不受影响（已实测） |
| κ(s) 的**分段属性** | 不受影响（κ 在 0.46 mm 上几乎不变） |
| 坐标的**绝对精度** | **受影响：0.46 mm** |
| `station_id` 的 1:1 对应 | 不受影响（UNIQUE 保证） |

**0.46 mm 对路面工程不是问题**（平整度以 mm 计，但那是**高程**；
平面坐标 0.46 mm 远低于任何施工与仿真的敏感度）。
**对 TruckSim 更不是问题** —— 它关心的是 κ(s) 的**分段形状**，不是 0.46 mm 的位置。

### 结论与处理

1. **不阻塞 MVP**。332 行照常产出，κ 正确，坐标误差 0.46 mm 可接受。
2. **必须记录，不得静默**。这正是本仓库反复强调的「看起来不对的数要能解释」。
3. **写入 `geometry_point` 的坐标来自库桩号**（经 `station_id` 关联），
   所以误差是**系统性的、可解释的**，不是随机噪声。
4. **若将来需要更高精度**：那是 `station_local_km` 的精度问题（`numeric(12,6)`
   → 更高），**属 schema 变更，按原则 IV 报工单**，本次不动。

### ★ 这条对测试的直接影响（重要）

**测试断言不得用「与 `.PM` 端点坐标相等」作判据** —— 库桩号已经把它降到 0.46 mm。
正确判据是：

- **在 `.PM` 自己的桩号上**求值 → 断言 3.171e-08 m 级（这才是公式的精度）
- **在库桩号上**求值 → 断言 0.46 mm 级（这是数据链路的精度）

**把两者混用会写出一个要么恒假、要么形同虚设的断言。** 已据此设计 T013。
