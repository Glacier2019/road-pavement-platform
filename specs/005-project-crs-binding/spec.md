# Feature Specification: 坐标基准跟着项目走

**Feature Branch**: `005-project-crs-binding`

**Created**: 2026-10-11

**Status**: Draft

**Input**: 平台服务多个设计项目时，每个项目有自己的坐标基准（带号／中央子午线／EPSG）。现在全平台共用一个配置文件和一个环境变量，必须让基准跟着项目走。

---

## 这个 feature 为什么存在

004 做完了「桩号 ↔ 经纬度」，精度实测到 **0.146 mm**。但那套换算认死了**一个**坐标基准：

```
crs.yaml 里写着 zone_number: 39 / central_meridian_deg: 117 / epsg: 4548
app.py 第 473 行调 load_crs()，不传路径
crs_path() 读环境变量 RP_CRS_CONFIG，默认 crs.yaml
```

一个部署一份配置。平台只服务一条路时没问题。**要商业化，就得服务很多条路。**

★ 但有一条实测结论改变了这个 feature 的大小 —— 见下面「已经查清的现场」。

---

## 已经查清的现场（2026-10-11 实测，不是推断）

### 1. 投影数学**已经是通用的**

```python
def forward(lat_deg, lon_deg, central_meridian_deg) -> (north, east)
def inverse(north, east, central_meridian_deg) -> (lat_deg, lon_deg)
```

★★ **中央子午线本来就是参数。** 换成 114°E 或 120°E 不需要改数学。

⇒ 这个 feature **不是**「重写投影」，是「**决定传哪个子午线进去**」。

### 2. 读配置的能力也已经是通用的

```python
def load_crs(path: str | pathlib.Path | None = None) -> dict
```

`load_crs` **已经能收路径**。004 的测试就在用这个能力，把测试指向仓库里的那份。

⇒ 缺的不是「能读多个配置」，是「**谁来选哪个路径**」。

### 3. 数据层级**已经在库里了**

```
design_project   ← 1 行：「毕设」，有 project_uid / designer / source_file
road_section.design_project_id   ← 路段已经指向项目
```

⇒ 不用新建「项目」这个概念。**项目和路段的树已经长好了。**

### 4. 但业务表上**一列坐标基准都没有**

全库 `information_schema.columns` 里，匹配 `srid|epsg|crs|zone|meridian` 的列只有一个来源：

```
spatial_ref_sys.srid / spatial_ref_sys.auth_srid     ← PostGIS 自己的登记表
road_section.climate_zone                            ← 气候分区，与坐标无关
```

★★ **所以缺口精确到一句话：项目到坐标基准的绑定，没有地方放。**

### 5. 坐标系登记表**已经在库里，而且很全**

| 项 | 实测 |
|---|---|
| `spatial_ref_sys` 行数 | **8500** |
| PostGIS 版本 | **3.4.3**（含 `postgis_topology`） |
| 39 带两种编码 | `4548`（无前缀，x_0=500000）／`4527`（有前缀，x_0=39500000） |
| 相邻带也在 | `4547`/`4526`（114°E）、`4549`/`4528`（120°E） |

⇒ **不用自己维护一份带号表。** 库里那份是 EPSG 官方的。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 平台能同时装下两个不同坐标基准的项目 (Priority: P1)

管理员把 A 项目（117°E 带）和 B 项目（114°E 带）都装进平台。用户查 A 项目里某个点的经纬度，和查 B 项目里某个点，**拿到的是各自正确的经纬度**，而不是「都按 117°E 算」。

**Why this priority**: 这是整个 feature 的存在理由。没有它，平台只能服务一条路，商业化的第一道门就过不去。

**Independent Test**: 造两个项目，给它们配不同的中央子午线。取两个**设计坐标完全相同**的点（同一个 `(x, y)`），分属两个项目。检查算出来的经度**必须不同**，且差**正好等于两条中央子午线之差**。再用一个「全平台一份配置」的对照，证明那时两个经度**会相同**。

**Acceptance Scenarios**:

1. **Given** 两个项目配了不同的中央子午线，**When** 查同一个 `(x, y)` 分属两个项目时的经纬度，**Then** 两个经度不同，差值等于两条中央子午线之差。
2. **Given** 一个项目没配坐标基准，**When** 查它的经纬度，**Then** 回答「这个项目没配基准」，**不是**默默用别的项目的基准顶上，**也不是**默默用 39 带顶上。
3. **Given** 一个项目配了一个库里不存在的 EPSG 编码，**When** 装这个配置，**Then** 当场报错，说明这个编码在 `spatial_ref_sys` 里查不到。

---

### User Story 2 - 现有的这条路**不用改一个字就继续能算** (Priority: P2)

「毕设」这个项目已经配好、已经验收到 0.146 mm。加了多项目能力之后，它的每一个换算结果**逐位不变**。

**Why this priority**: 004 的 39 项验收、21 个契约套件都建立在这条路的正确性上。**通用化不能以破坏已验收的精度为代价。** 这一条排 P2 是因为它不产生新价值，但它是一道必须过的闸。

**Independent Test**: 把 004 的整套契约测试原样再跑一遍，**全部绿**；并且逐条比对若干代表性桩号的经纬度，**与通用化之前逐位相同**。

**Acceptance Scenarios**:

1. **Given** 004 已验收的那条路，**When** 通用化之后重跑全部契约测试，**Then** 通过数与之前相同，无一失败。
2. **Given** 一个代表性桩号，**When** 通用化前后各算一次经纬度，**Then** 浮点逐位相同。

---

### User Story 3 - 接手的人能一眼看出「这条路用的是哪个基准、凭什么」 (Priority: P3)

新人打开平台，想知道某个项目为什么是 117°E 带。他不用翻 git 历史、不用问人，**在平台上直接查得到**，而且能看到这个判断依据是什么、什么时候定的、置信到什么程度。

**Why this priority**: 004 已经证明了「基准猜错 → 位置差几百公里 → 在局部视图里看不出来」。**规模化之后，这个错误会乘以项目数。**

**Independent Test**: 对任意一个已配基准的项目，在不读代码的前提下，查到它的带号、中央子午线、EPSG，以及 `assumed` 标记和推断依据。

**Acceptance Scenarios**:

1. **Given** 任一项目，**When** 查它的坐标基准，**Then** 拿到带号、中央子午线、EPSG 三件套，以及「这个值是确认的还是推断的」。
2. **Given** 一个基准是**推断**的项目，**When** 查它，**Then** 回答里必须带上推断依据，**不允许**只给一个数字。

---

### Edge Cases

<!--
  ★ 下面每一条都是实测或已裁决的，不是想象出来的边界。
-->

- **一个项目里的两个路段配了不同的带号** → 两级基准都存在（Q1 已定），所以这一条**必然会发生**。怎么处理见 **Q1b**：这是本 feature 现在最要紧的未决问题。
- **项目配了基准，但某条路段的设计坐标其实是另一套基准的**（录入时弄错） → 换算会给出一个「看着正常但是错的」经纬度。**必须有一道能拦住它的检查。** 004 的教训：`offset_m` 那种「如实报残差」的做法，比「拒绝」更有用，但**必须报**。
- **项目没配基准** → 不许回落到全局默认，不许回落到 39 带。必须是一个**有类型的「没有」**（004 已确立的 `position_source` 三值模式）。
- **基准换了**（项目从 117°E 挪到 114°E） → 换算结果必须跟着变。**不许出现「改了配置但结果没动」** —— 004 抓到过一次一模一样的事故：`crs.yaml` 是**构建时** COPY 进镜像的，所以 `docker compose restart` 改了配置却**逐位不变**，验收还通过了。**那是一次静默空转。**
- **`spatial_ref_sys` 里查不到的 EPSG** → 装载时就要拒，不许等到第一次换算才炸。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 平台 MUST 让坐标基准**按项目区分**，**同时按路段区分**（Q1 已定：两级都要有）。
- **FR-002**: 平台 MUST 在**每一个**涉及经纬度的回答里，说得清这个答案用的是**哪个**基准，以及**这个基准来自哪一级**（项目级／路段级）。★ **只报「用了哪个基准」不够** —— 两级都存在时，还得分得清是继承来的还是路段自己写的。
- **FR-003**: 查一个**两级都没配**基准的对象时，系统 MUST 返回一个有类型的「没有」，并说明原因。**MUST NOT** 回落到任何全局默认值或 39 带。★ 真实用例已存在：路段 1「滨海大通道试验段」`design_project_id = NULL`。
- **FR-004**: 基准配置 MUST 能在**不改代码、不重新构建镜像**的前提下新增或修改。★ 004 的实测：改配置必须走 `up -d --build`，`restart` 是静默空转。
- **FR-005**: 装载一个基准时，系统 MUST 校验它和 `spatial_ref_sys` 里登记的编码一致；查不到的编码 MUST 当场拒绝。
- **FR-006**: 平台 MUST 保留「这个基准是确认的还是推断的」这个区分，以及推断的依据。★ 004 已确立：`ready` 说能不能用，`assumed` 说值可不可信。
- **FR-007**: 通用化之后，004 已验收的换算精度 MUST NOT 变差。判据：同一个输入，通用化前后的经纬度**浮点逐位相同**。
- **FR-008**: 平台 MUST 在同一个部署里同时持有**至少两个**不同基准的项目，且互不干扰。
- **FR-009**: 两级基准**取值不同**时，系统 MUST **拒绝**并报错（Q1b 已定 B）。**MUST NOT** 让任何一级静默生效。
- **FR-010**: 当路段**没有所属项目**时（`design_project_id` 为 NULL），路段级基准 MUST 单独生效，**MUST NOT** 因为「没有项目可以比对」而拒绝。★ 实测用例：路段 1。
- **FR-011**: 两级**都没有**基准时，按 FR-003 返回有类型的「没有」。
- **FR-012**: 基准 MUST 存放在**数据库**里（Q2 已定 A），挂在与它同级的那张表上（项目级挂 `design_project`，路段级挂 `road_section`）。**MUST NOT** 新增运行时读取的配置文件。
- **FR-013**: 现有的五个 `crs.yaml` 消费者 MUST 继续能拿到它们要的值（见 [Q3](#待澄清的问题)）。★ 其中两个是**纯标准库 Python 脚本**与 **JS 脚本**，MUST NOT 要求它们连数据库。
- **FR-014**: 如果库与 `crs.yaml` 并存，系统 MUST 有一道**「文件与库一致」的检查**，不一致时**必须报错**。★ 光有生成步骤不够 —— 004 已经踩过一次「改了配置但结果没动」，这次的风险是「改了库但文件没跟上」。
- **FR-015**: 「这个基准是确认的还是推断的」以及推断依据，MUST 随基准一起存放，MUST NOT 只留在文件里。
- **FR-016**: `spatial_ref_sys` MUST 只用于**校验** EPSG 编码，MUST NOT 参与每次换算（见 [Q4](#待澄清的问题)）。★ 004 的整套验证刻意做成不连库，换算改走 PostGIS 会废掉这个性质。

### Key Entities *(include if feature involves data)*

- **设计项目（design_project）**：已存在。1 行：「毕设」。有 `project_uid`、`project_name`、`designer`、`source_file`。★ **它现在没有任何坐标基准字段 —— 这是本 feature 要补的两处之一。**
- **路段（road_section）**：已存在。已有 `design_project_id` 指向项目。2 行（其中路段 1 的 `design_project_id` 是 NULL）。★ **它现在也没有任何坐标基准字段 —— 这是要补的另一处。**
- **坐标基准（本次要新增的东西）**：至少要有带号、中央子午线、EPSG、`assumed` 标记、推断依据。**两级都要挂（Q1 已定）；两级不一致时算谁的见 Q1b；存在哪里见 Q2。**
- **坐标系登记表（spatial_ref_sys）**：已存在，8500 行，PostGIS 3.4.3 自带。**本 feature 只需要读它，不需要维护它。**

## 待澄清的问题

★ 按平台方「一个一个确定」的规矩逐条提出。**四条全部已定（2026-10-11）。**

★ 其中 **Q1、Q1b、Q2 由平台方直接裁决**；**Q3、Q4 平台方答「继续」（即按建议推进），因此这两条是可推翻的** —— 若不同意，说一声即改。

★ 每条都保留了**被否掉的选项与理由**。理由比结论重要：结论可以改，理由会在别处复用。

### Q1 ✅ 已定（2026-10-11）：**基准在项目和路段两级都要有**

平台方答：「**A、B 一起**」。

⇒ **不再追问「选哪一级」，两级都要。**

| 层级 | 现状 | 本 feature 要补的 |
|---|---|---|
| **项目（`design_project`）** | 表已存在，1 行，**没有任何基准字段** | 基准字段 |
| **路段（`road_section`）** | 表已存在，2 行，**没有任何基准字段** | 基准字段 |

★ 那条工程事实仍然成立，而且**现在变得更要紧**：3° 带在 25°N 附近宽约 **250 km**。一条长高速**可能**跨带，但工程上跨带时的常规做法是**全线选一个中央子午线**（任意带／抵偿投影面），**不是**分成两段各用各的带。理由是桩号连续 —— 分段换带会让同一份坐标的意思在中途变掉。

★★ **它的含义是：路段级基准绝大多数时候应当等于项目级。** 于是「两级都有」立刻派生出一个必须回答的问题 —— 两级不一致时算谁的。见 **Q1b**。

★ 实测补充（2026-10-11，问这个问题之前查的）：

```
路段 1「滨海大通道试验段」| design_project_id = NULL   ← 不属于任何项目
路段 6「毕设」           | design_project_id = 2      ← 毕设
```

**平台现在就已经有一个「没有项目」的路段。** 它同时 0 线元 / 0 地面点，所以本来就没有坐标。两级都有基准之后，它**两级都没有** —— 这正是 FR-003 要处理的「有类型的没有」，而且用的是真实数据，不是造的。

### Q1b ✅ 已定（2026-10-11）：**两级必须一致，不等就报错**

平台方答：「**B：必须一致，不等就报错**」。

★ 代价已记录在案：将来真需要跨带，得**先改这条规则**，而不是「配一下就行」。这是明知的取舍。

★★ **这个选择改变了路段级基准的性质。** 它**不是第二个真相来源**，而是一道**冗余校验** —— 项目级才是权威，路段级是「这条路段自己声明的值」，它的作用是让人**必须**在某条路段上写字才能表达「我跟项目不一样」，而一旦不一致就当场报错。

#### 按 B 推出来的四条子规则（如果有一条不对，说一声）

| 情形 | 规则 | 为什么 |
|---|---|---|
| 项目有、路段有、**相等** | 通过 | 正常态 |
| 项目有、路段有、**不等** | ★ **报错** | 这就是 B 要拦的 |
| 项目有、路段**没填** | 通过，用项目的 | 路段级是冗余校验，不是必填项 |
| **项目没有**（没配，或路段没有 `design_project_id`）、路段有 | ★ **通过，用路段的** | 见下 |

★★ 最后一条是要紧的：**如果一个路段根本没有项目，路段级基准就是它唯一的基准来源。** 实测里就有这么一个路段（路段 1，`design_project_id = NULL`）。如果这条规则判为「报错」，那个路段就**永远无法定位** —— 那是把一条可以用的数据锁死。

★ 反过来，**两级都没有** → 返回「没配基准」（FR-003 的那个有类型的「没有」）。

★ 004 的教训直接适用：**「看着正常的错值」比「明确的缺失」危险得多。** 一个静默生效的错基准会让位置差几百公里，而在局部视图里看不出来。

### Q2 ✅ 已定（2026-10-11）：**存在数据库里**

平台方答：「**A：数据库**」。

⇒ 基准就是 `design_project` 和 `road_section` 上的字段。**不新建配置文件，也不新增文件读取路径。**

★ 这个选择不用新增任何机制就能满足 FR-004：项目已经在库里，api 的环境变量里已经有 `PG_DSN`（**它本来就在连 PostGIS**），改一行 SQL 就生效，不用构建、不用挂载。

★ 被否掉的那条路，理由值得留档：**「每个项目一个配置文件」需要一个「项目 → 文件」的映射**（靠命名约定就是隐式绑定，会悄悄漂移；放数据库则文件本身多余）。**它会把本 feature 要解决的问题原样再造一遍**，只是换了个名字。另外实测 `api` 服务的 `volumes` 是 `None` —— 一个挂载都没有，所以配置文件只能靠构建时 COPY，与 FR-004 直接冲突。

### Q3 ✅ 已定（2026-10-11）：**已经存在的 `crs.yaml` 保留，但改成从库导出的产物**

★ **问这个问题之前核出的实测事实：`crs.yaml` 有五个消费者，跨 Python 与 JavaScript。**

| 消费者 | 读什么 | 怎么读 |
|---|---|---|
| `modules/M6-api/geo.py`（`load_crs`） | 全部字段 | PyYAML；路径由 `RP_CRS_CONFIG` 决定，默认 `/app/crs.yaml` |
| `modules/M9-console/app.py:96` | 全部字段 | 自己解析；失败会返回 `{"_error": …}` |
| `simulator/crg/export_viewer_mesh.py` | **只读 `ready` / `assumed`** | ★ **故意不引 PyYAML**，用正则定点匹配 |
| `tests/integration/sim_inline_script.mjs:66,105` | 同上两个标记 | ★ **JS 里手写了一个「极简 YAML 读取」** |
| 三套契约测试 | 存在性、`assumed`、`evidence`、清单值一致性 | 直接读文本 |

★★ **这条事实决定了 Q3 不能是「把文件删掉」。** 其中两个消费者是**纯标准库 Python 脚本**和 **JS 脚本** —— 让它们去读 Postgres 分别要引驱动、引 JS 的 PG 客户端，而且会丢掉 `export_viewer_mesh.py` 那条「标准库-only，能在任意目录直接跑」的属性。

| 选项 | 做法 | 代价 |
|---|---|---|
| **(a) 库为准，文件改成产物** | 文件由库**导出**，保留所有现有消费者；加一道「文件与库一致」的守卫 | 多一个生成步骤；★ 文件可能过期 |
| **(b) 库为准，消费者各自读库** | 删掉文件 | JS 与标准库脚本都要能连库；丢掉「任意目录直接跑」 |
| **(c) 文件只服务单项目，多项目走库** | 两套来源并存 | ★ 两套真相 |

#### ✅ 已定（2026-10-12）：**取 (a)**，文件改为从库导出的产物

★★ **这条由平台方直接裁决**（2026-10-12，逐条复核时确认）。**不是「按建议推进」。**

#### 三个选项在商业化下的真实分数

| 选项 | 商业化下是什么样 |
|---|---|
| (a) 只自己算 | 代码**是对的**，但所有精度数字都是自证 —— **卖不出去这个「对」** |
| (b) 只用 PostGIS | 换投影免费，但几何**变成必须有库**，离线测试全废 |
| **(c) 自己算 + PostGIS 当标尺** ✅ | **保留全部既有性质，同时拿到独立证据** |

★ 理由一（保留既有性质）：004 那套手写高斯-克吕格已经与 PostGIS 一致到 9 µm。**换掉它，是拿一个已被独立印证到 9 µm 的实现，去换一个把几何绑死在数据库上的实现。**

★ 理由二（也是选 (c) 而非 (a) 的关键）：`test_region_frame.py` 开头写着「运行（不需要数据库、不需要容器、不需要网络）」。**(c) 保住这条** —— 标尺只在契约测试里用，**不在生产路径上**，所以不加运行时开销、不破坏离线可跑。

★★ 理由三（**通用性的具体含义**）：现在那四十行只实现了**一个投影族**：高斯-克吕格。一个要卖到中国以外的产品需要 UTM / Lambert / State Plane。
- **只有 (a)**：每加一个投影族就新写一份实现，**而且没有独立核对**。
- **有了 (c)**：每加一个投影族，加一个 SRID，**让同一套比对去验它**。

#### 选 (c) 的代价（必须写进文档）

- **两套实现要能对得上** ⇒ 比对必须进契约测试，红了要改。
- ★★ **一旦变换跨了基准**（如 WGS84 → CGCS2000），两个实现**可能合法地不一致** —— 那时不能简单判红，得先判「谁该对」。本例不成问题：做的是 **CGCS2000 → CGCS2000 同基准**投影，没有基准平移。

- **SC-002**: **★ 对照判据。** 取两个**设计坐标逐位相同**的点，分属两个不同基准的项目。两者的经度**必须不同**，且差值**等于两条中央子午线之差**（容差 1e-9 度）。★ 对照组：把基准改回全平台一份，这两个经度**必须变得相同**。**没有这个对照，SC-001 可以被「假装有基准」通过。**
