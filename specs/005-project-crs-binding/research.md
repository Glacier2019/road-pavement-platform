## R3. ★★ 路段 → 项目的 join **已经在生产路径上**

### 测法
读 `GeRepository.SECTIONS_SQL` / `ONE_SECTION_SQL` 原文。

### 事实

```sql
SECTIONS_SQL:
  SELECT s.id, s.section_name, ..., l.line_code, ...,
         p.id AS project_id, p.project_name, p.project_uid, p.designer, ...
  FROM road_section s
  JOIN      road_line         l ON l.id = s.line_id
  LEFT JOIN design_project    p ON p.id = s.design_project_id     -- ★★★ 已在
  LEFT JOIN section_design_attr a ON a.section_id = s.id
  ORDER BY l.line_code, s.id
```

`ONE_SECTION_SQL` 有同一个 `LEFT JOIN design_project p`。

### 结论（三条，全部影响实现面）

1. **不需要新建 join。** 加基准列 = 在**已有的 SELECT 列表**和**已有的关联**上多加几列。
2. ★★ **用的是 `LEFT JOIN`，不是 `INNER JOIN`** ⇒ **路段 1 那条 `design_project_id = NULL` 现在就已经能正常返回**（`project_id` 为 NULL）。**FR-010「没有项目的路段」在数据层已经是处理过的形状，不是新边界。**
3. ★★★ **`LEFT JOIN` 同时意味着「项目级基准」天然可以为 NULL** ⇒ **FR-003 的「有类型的没有」在这条路径上自动成立。**

### 影响
不新增 DAO 方法、不新增端点。`sections()` / `section(id)` 直接多带几列即可。

### ★★ 两条要紧的推论

**推论一（这条改动最容易破的线）：** 那条 AST 断言**只扫 `app.py` 一个文件**，而 psycopg 在镜像里是**装着**的。⇒ **在 `geo.py` 里加连接会绕过断言的字面，但违反宪法 II 的意图。** 所以本 feature **必须补一条「`geo.py` 里不得出现 psycopg」的断言** —— 005 恰恰是「给几何域加数据来源」的一次改动，是最容易顺手在那里连库的一次。

**推论二（形状）：** `geo.py` 必须保持**零数据库、纯函数**。基准由 `app.py` 经 `dao.ge` 取到，**作为参数传进去**。这与现有的 `station_to_lonlat(elements, ...)` 完全同形 —— 几何数据本来就是外部传进来的。

### 结论
**DAO 层加读基准的能力，`geo.py` 只改「基准从哪来」，不获得任何新的数据来源。**

## R6. 两级不一致该在哪里拦（Q1b = B 的落地）

### 候选

| 方案 | 强制点 | 评价 |
|---|---|---|
| **(a) DB 层：触发器 / 约束** | 写入时 | ★ 最符合宪法 II「结构上做不到」。但跨表比较需要触发器，`section_design_attr` 那种「派生表」模式在本仓库已有先例可循 |

## R10. ★★ 带号 ↔ SRID ↔ 中央子午线：一条真规则，和一个把我的验证骗过去的陷阱

### 起因

写 quickstart 第 6 步时，我需要在里面填一个「中央子午线 108（36 带）」的 EPSG。**那个 `4545` 是我凭记忆填的。** 既然本文件通篇在讲「不许凭记忆断言」，那就得去验它。

### ★★★ 第一次验证是错的，而它给出了一个理直气壮的空结果

```
SELECT srid FROM spatial_ref_sys
WHERE proj4text LIKE '%+lon_0=108%' AND proj4text LIKE '%gauss%'
→ （空）
```

**读到「空」的第一反应是「4545 不存在」。** 但空结果的真正原因是：**那串 `proj4text` 里根本没有 "gauss" 这个词** —— 高斯-克吕格在 PROJ 里的写法是 `+proj=tmerc`（横轴墨卡托）。

★★ **一个筛错的查询，和一次真的「不存在」，返回的东西长得一模一样。** 这正是宪法 V 那条「**「没去看」≠「看了没有」**」的又一件实例 —— 而这一次，**做这件事的人是在试图验证自己的一个断言。**

### 用对口径之后：`4545` 存在，而且我的值恰好是对的

```
4548 | +proj=tmerc +lat_0=0 +lon_0=117 +k=1 +x_0=500000 +y_0=0 +ellps=GRS80 +units=m +no_defs
4545 | +proj=tmerc +lat_0=0 +lon_0=108 +k=1 +x_0=500000 +y_0=0 +ellps=GRS80 +units=m +no_defs
```

★ **除 `lon_0` 外逐字节相同。** 顺带的两个真发现：

1. **`ellps=GRS80`。** 而 `geo.py` 里手写的是 `a=6378137.0; f=1/298.257222101` —— **那就是 GRS80 的参数**。⇒ 平台的投影数学与登记表里的椭球**是一致的**，这是一处真的交叉印证（不是巧合，是可以算出来的）。
2. **两个系列并存**：
   - `x_0=500000` ⇒ 不带带号前缀
   - `x_0=38500000 / 39500000 / 40500000` ⇒ 带带号前缀（`4526/4527/4528` 是后者）

### ★★ 于是有一条可校验的真规则（21/21 无反例）

```
对 25..45 带，逐个查 spatial_ref_sys：
    SRID                = 带号 + 4509
    lon_0               = 带号 × 3
    x_0                 = 500000
```

实测结果：**21 个带全部命中，反例 0。**

| 带号 | 36 | 37 | 38 | 39 | 40 | 41 |
|---|---|---|---|---|---|---|
| SRID | 4545 | 4546 | 4547 | **4548** | 4549 | 4550 |
| CM | 108 | 111 | 114 | **117** | 120 | 123 |

★ 平台今天用的 **39 带 / 117° / 4548** 正好落在这条规则上。

### 这条发现怎么用 —— 两处，方向相反

**（一）它让 data-model 的 I1 不变量变成一条真规则，而不是一张硬编码的表。**

```
crs_central_meridian_deg == crs_zone_number * 3            （3 度带族）
★★ 2026-10-12 作废：这条**不得进代码**（那个 3 是硬编码常量）。见 R11 补记。
crs_epsg                 MUST 在 spatial_ref_sys.srid 里查得到
```

★★ **注意这两句是分开的**：**中央子午线用算式，EPSG 用查表。** 不把 `SRID = 带号 + 4509` 写进代码 —— 因为 `test_sim_track.py` 有一条既有守卫逐字写着「**带号是配置项，不是代码里的常量**」。把这条规律硬化成代码常量，就正好违反它。

**（二）★ 它是 FR-005 的直接论据。**

FR-005 要求「校验与 `spatial_ref_sys` 登记一致；查不到 MUST 当场拒绝」。上面那个空结果的教训说明：**当「校验」本身可能是筛错的时候，校验必须打到权威表上，而不是打到自己写的规则上。** 一条规律在 25..45 带上成立，不代表 46 带成立，更不代表某个项目的 `proj4text` 就是它该有的那个。

### ★ 留档：本仓库「空结果被读成否定结论」的第 3 次

| # | 位置 | 空结果被读成了 |
|---|---|---|
| 1 | 004 T035 | 前缀过滤的路径比对 ⇒ 8 条「实现里没有」，实则都在 |
| 2 | 004 §12 | 猜的控制点给出 `off_corridor` ⇒ 被判成「分带错了」，实则控制点选错 |
| 3 | **本次** | 加错筛词 ⇒ **「4545 不存在」**，实则存在 |

★★ **三次的形状完全一样：查询/取样本身错了，而结果读起来像一个关于世界的结论。** 所以「查不到」这个结论**必须带着查询一起报**。

## R11. ★★★★★ 手写投影与 PostGIS 的独立对拍：9 µm —— 而在此之前，平台关于自己精度的每一个数都是自证

### 起因：Q4 复核时问的是「要通用商业化选哪个」

商业化要的不是「准」，是「**准这件事凭什么让客户信**」。于是去核一个更基本的问题：**这个投影，被外部权威核对过吗？**

### ★★★ 核出来的事：没有。今天全部证据都是自证

| 位置 | 原文 | 它实际量的是什么 |
|---|---|---|
| `test_region_frame.py:421-422` | `forward(lat, lon, 117.0)` 再 `inverse(n, e, 117.0)` | ★ **同一份代码正算再反算** ⇒ 量的是**自洽**，不是正确 |
| 同文件 §12「实测残差 0.0398 mm」 | 上一行注释：「拿**路线自己的点**回灌」 | ★ 仍是自己跟自己 |
| 同文件 `:433-438` bbox 检查 | `25.16 < lat_min < 25.18` | ★ 一个**约 2 km 宽**的窗口 —— 验「落在大概位置」，**没验「算对了」** |

★★ 全仓库 `grep 'pyproj\|ST_Transform\|gdal'` **零命中**。`geo.py:32` 有一整节标题叫「为什么手写投影而不引 pyproj」。

⇒ ★★ **一个内部一致、整体偏掉的投影，能通过今天全部这些测试。** 这不是说现行实现错了 —— R8 已经证明它是准的。**是说它「准」这件事，没有任何独立证据。**

### ★★★★★ 而权威就在同一个数据库里：PostGIS 3.4.3 / PROJ 7.2.1

`ST_Transform(…, 4326 → 4548)` 实测（三个点，覆盖路线两端与中心）：

| 点 | 手写 north | PostGIS north | 差 |
|---|---|---|---|
| 25.18596 / 117.35926（中心） | 2786702.067596 | 2786702.067587 | **9 µm** |
| 25.16789 / 117.34292（西南） | 2784696.035740 | 2784696.035731 | 9 µm |
| 25.20878 / 117.37376（东北） | 2789233.985441 | 2789233.985432 | 9 µm |
| 三个点的 east | — | — | **逐位相同** |

★★★ **两个独立实现一致到 9 µm。**

★ 而 **9 µm 比平台自己报的 50.8 µm 往返误差还紧** ⇒ 那 50.8 µm 主要来自**反算**的级数截断，**正算本身是准的**。
★ 另有一条自洽性：登记表 `4548` 的 `proj4text` 写着 `ellps=GRS80`，而 `geo.py` 手写的 `a=6378137.0` / `f=1/298.257222101` **正是 GRS80 的两个参数**（R10 已记）。

### 这条事实怎么用（Q4 定案为「手写为生产路径，PostGIS 只做测试标尺」）

| 选项 | 商业化下是什么样 |
|---|---|
| (a) 只自己算 | 代码**是对的**，但所有精度数字都是自证 —— **卖不出去这个「对」** |
| (b) 只用 PostGIS | 换投影免费，但几何**变成必须有库**，离线测试全废 |
| **(c)** ✅ | **保留全部既有性质，同时拿到独立证据** |

★★ **标尺只在契约测试里用，不在生产路径上** ⇒ 不加运行时开销，且保住 `test_region_frame.py` 那句「不需要数据库、不需要容器、不需要网络」。

★★★ **通用性的具体含义**：现在那四十行只实现**一个投影族**（高斯-克吕格）。要卖到中国以外需要 UTM / Lambert / State Plane。
- **只有 (a)**：每加一个投影族就新写一份实现，**而且没有独立核对**。
- **有了 (c)**：每加一个投影族，加一个 SRID，**让同一套比对去验它**。

### 选 (c) 的代价（写进文档）

### ★★ R11 补记（2026-10-12，同日）：平台方定下长期准则「以后都要用通用商业化为目的去选择」

这条准则立刻找出了**我自己设计里的一个缺陷**，两次尝试，**两次都被实测否掉**：

#### 否掉之一：`crs_central_meridian_deg == crs_zone_number * 3`（data-model.md I1 的算式）

★ 那个 **`3` 就是硬编码的常量** —— 而 `test_sim_track.py` 的守卫写的是「带号是配置项，**不是代码里的常量**」。**我引用了那条守卫，然后自己写了一个违反它的算式。**

实测否证（`spatial_ref_sys`）：

| srid | 3 度带算式 `(srid−4509)×3` | 6 度带猜测 `(srid−4508)×3` | 实际 `+lon_0` |
|---|---|---|---|
| 4545 | 36×3 = **108** ✓ | 37×3 = 111 ✗ | **108** |
| 4524 | — | 16×3 = 48 ✗（它实际是 6 度带第 18 带） | **108** |

⇒ **两个「规律」都是我猜的。一个偶然对上，一个直接错。** ★ 该算式 MUST NOT 进代码。

#### 否掉之二：改用「登记表的 `+lon_0`」当中央子午线来源

★ 这个看起来更普适 —— **实测也不普适**：

| 投影族 | 有 `+lon_0` 吗 | 例 |
|---|---|---|
| tmerc（横轴墨卡托 / 高斯-克吕格） | 有 | 4548 → `+lon_0=117` |
| lcc（兰勃特等角圆锥） | 有 | 2154 → `3`；2230 → `-116.25` |
| aea（阿尔伯斯等积） | 有 | 5070 → `-96` |
| **utm** | ★ **没有** | 32650 / 32633 / 26915 全部无 |
| **4326 地理坐标** | ★ **没有**（本来就没有中央子午线） | — |

★★ **全表 8500 个 SRID，有 `+lon_0` 的只有 5818 个，2682 个没有。** ⇒ `+lon_0` **不能**作为通用来源。

#### ★★★★★ 而唯一普适的东西是 SRID 本身

实测「**只给 SRID、不给中央子午线**」的换算，全部成功：

| 目标 SRID | 投影族 | `ST_Transform` 结果 |
|---|---|---|
| 4548 | tmerc（中国 3 度带） | east = 536212.705 ★ 与手写 536212.704510 一致 |
| 32650 | utm | east = 536198.219 |
| 2154 | lcc（法国 Lambert-93） | east = 652301.565 |
| 5070 | aea（美国等积） | east = **0.000** ★★ **不是失败** —— 那个点（−96, 38）**正是它的投影原点** |

#### ⇒ 这条准则对 005 的直接结论（**待平台方裁决**）

```kv
权威字段: crs_epsg（SRID）—— 全球唯一可解析，8500 个全部能算
可选注释: crs_zone_number / crs_central_meridian_deg / crs_zone_width_deg
          有则与 SRID 自洽，无则不得报错
换算分两层: 第一层手写（快、离线，只覆盖已实现的投影族，需 CM）
            第二层 PostGIS（普适，只需 SRID）
            用了哪层写进响应
```

★★★ **理由**：UTM 和 Lambert **没有「带号」这个概念**（或含义不同），Lambert/aea 的「中央子午线」也不是分带的产物。
**把带号做成必填字段，等于把数据模型钉死在中国高斯-克吕格上** —— 而这是要把产品卖出去时第一个要拆掉的东西。
