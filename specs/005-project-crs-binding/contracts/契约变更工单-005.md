- **契约编号**：② 表结构 ＋ ③ 数据出口(DAO) ＋ ④ 服务接口
- **提议人 / 日期**：005-project-crs-binding / 2026-10-11
- **变更内容（精确到字段/主题/路径）**：

### ② 表结构（`10_ddl_v0.6.sql` + 新迁移）

`design_project` 与 `road_section` **各加七个列**（两处同名同类型）：

```
crs_zone_number           smallint
crs_central_meridian_deg  numeric(9,6)
crs_epsg                  integer
crs_zone_width_deg        numeric(4,2)
crs_assumed               boolean
crs_evidence              text
```

★ 列名统一带 `crs_` 前缀。实测：现状下全库 `information_schema.columns` 扫
`srid|epsg|crs|zone|meridian` **零个业务列命中** —— 加前缀后**命中即全部**，便于审计。

### ③ 数据出口（`M3-rpdao`）

- `GeRepository.SECTIONS_SQL` / `ONE_SECTION_SQL`：**只加列，不加 join**。
  ★ 实测两条 SQL **已经有** `LEFT JOIN design_project p ON p.id = s.design_project_id`。
- `GeRepository.sections()` / `section(section_id)`：**签名不变**，返回的行多带基准列。
- ★ **不新增 DAO 方法**，不新增端点。

### ④ 服务接口（`contracts/openapi/m6-gateway.geo.*.yaml`）

**新版本 v0.2**（`m6-gateway.geo.v0.2.yaml`），v0.1 **不就地改**。

四个已有路径的响应各增两个字段：

```
crs_source      enum: [project, section]      # 这个基准是在哪一级被写下的
crs_assumed     boolean                       # 值可不可信（继承 004 的语义）
```

`/geo` 与 `/geo/reverse` 另增：

```
crs_zone_number / crs_central_meridian_deg / crs_epsg
```

★ **字段名 MUST 以 `schema:` 块声明**（带 `properties` + `required`），
**MUST NOT 只写在 `description:` 的 prose 里** —— v0.1 的头部记着这条教训：
「prose 写的契约不是契约，是注释」，它静默漂了很久，**而下游文档正是从这里抄错的**。

- **变更原因（不改就做不下去的具体卡点）**：

★★ **「用哪个坐标基准」现在是部署级的，而且只是一个环境变量。**

```python
# app.py:466-474 —— 唯一调用点，空参
def _geo_crs() -> dict[str, Any]:
    return geo_mod.load_crs()

# geo.py:284-295
return pathlib.Path(os.getenv("RP_CRS_CONFIG", "crs.yaml"))
```

⇒ **全平台一份基准。** 两个不同中央子午线的项目**无法在同一个部署里共存**：
后一个的桩号会被前一个的带号投影到几百公里外，**而且路的形状完全正确、不报任何错**。

★★ 这不是假设 —— 004 的验收里实测过：把带号从 117 改成 114，经度**正好平移 3.000°**，
而所有几何、所有桩号、所有形状**一点没变**。**它是静默的。**

## ★ 本工单自己遵守的两条规矩

1. **字段名以 `schema:` 声明，不写在 prose 里。** v0.1 的教训：一份「不参与校验」的摘要可以漂到与实现完全无关而没人发现。
2. **本工单声明的一切，实现里必须存在。** 004 犯过一次：在修「声明了但不存在」的缺陷时，**又声明了一个不存在的东西**（加了一条没有实现的 `/geo/reverse/bands` 路径）。**修一条谎的时候最容易再说一条谎。**
