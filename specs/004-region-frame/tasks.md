## ⚠️ 一处与 spec 优先级的偏离，以及理由

spec 把 **US1（桩号↔经纬度）标为 P1**，与实现顺序一致，无须偏离。
但要注意：**US1 所需的全部零件是纯计算，没有一条依赖前端。**
所以 Phase 2（投影与线元求值）与 Phase 3（暴露成可核对的能力）之间的分界是
「纯函数」与「接口」，不是「底层」与「上层」。

★ 这个分界是刻意的：**SC-007 要求换算能在没有浏览器、没有地图服务的环境里
完整验证。** 把纯计算放进 Foundational，就等于让整个 MVP 在离线状态下可验 ——
这不是实现顺序问题，是**可验证性**问题。

## ⚠️ 实施阶段出现的第三条**计划外改动**：spec 的 US3 判据**自己满足不了**

### 现象：spec 的三处说法互相打架

| 位置 | 原话 |
|---|---|
| Key Entities | 「**线形单元（alignment_element）**：33 段 …… **地理坐标的唯一来源。**」 |
| Edge Cases | 「**两个路段桩号语义不同**：毕设 `K0+000` 与滨海 `K4635+000` 是**两个不同位置**。」 |
| US3 Independent Test | 「**3 个断面**算出的经纬度，必须落在 US1 给出的路线包围盒内。」 |

前两句都对。**第三句在前两句成立时不可能满足。**

### 实测数据（活库，2026-10-11）

| 路段 | 桩号范围 | 线元 | 断面 |
|---|---|---|---|
| 1 滨海大通道试验段 | 4635.000 → 4654.701 km | **0** | **2** |
| 6 毕设 | 0.000 → 5.805421 km | **33** | **1** |

断面 1（`K4635+710`）与断面 2（`K4640+000`）挂在**路段 1** 上，
而路段 1 **一个线形单元都没有**。按 spec 自己的定义（线形是地理坐标的唯一来源），
这两个断面的位置**不存在** —— 它们永远落不进路段 6 的包围盒。

★★★★ **所以那条判据只能靠"悄悄丢掉 2 个断面"来通过。**
一条要靠丢数据才能满足的验收判据，比没有判据更坏：它看起来验过了。

### 这不是"顺手改判据"，是判据本身的形状错了

★★★ **「全部 N 项都落在包围盒 B 内」这条句式，默认了 N 项都属于 B 的主体。**
一旦其中有一项不属于（或它所属的主体没有坐标），这条判据就**无法被诚实地满足**。
真正要检验的不是"N 项都在框里"，而是**"每一项的位置是怎么来的，说得出来吗"**。

### 改法：位置的来源做成一等公民（三值 + 理由）

```
position_source ∈ { "stored", "computed_from_station", "unavailable" }
```

| 取值 | 含义 | 实测例子 |
|---|---|---|
| `stored` | 库里有经纬度，直接用 | 商用平台上的 GNSS 实测断面 |
| `computed_from_station` | 库里没有，**由桩号换算** | `K2+900` → `25.188125°N / 117.357660°E` |
| `unavailable` | 换算不出来，**附 `unavailable_reason`** | 路段 1 的两个断面 |

★ 为什么不是「能算就算、算不出就跳过」：**跳过 = 缺失变成静默**，
和「读成 0」是同一个错误的两种表现 —— 都把「没有位置」当成了一个位置。

★★ `unavailable` 走 **200 而不是 404**：它是**正常的答案**，
不是「资源不存在」。（但**路段本身不存在**仍然是 404 —— 两件事必须分开，
否则写错一个 `section_id` 得到的是「没有数据」而不是「没有这个路段」。）

### FR-010 因此变成**结构性**保证

`lat_deg` / `lon_deg` 两个键**只在真有位置时才出现**。

无条件取用的人拿到的是 `KeyError`（Python）/ `undefined`（JS），
**而不是 `(0, 0)`** —— 这个错误**无法静默发生**。
比"约定大家要判空"强的地方在于：约定会被绕过，缺键不会。

★ 元测试**已注入并实测变红**：把 `geo.py` 的判空改成 `lat_stored or 0.0` 后，
`(0,0)` 被当成合法位置，而「位置必须落在**本路段自己的**区域帧内」这条判据抓住它。

### 溯源标签取自**数据自己的枚举**，不取自序列号

T032 原文写的是 `SIMWIM01`（一个序列号）。实施时改成读
`sensor_install.install_mode`，实测取值 `埋入式` / `表面式` / **`仿真`**。

| 判断 | 依据 |
|---|---|
| `simulated = True` | `install_mode == "仿真"` |
| `simulated = False` | `install_mode ∈ {埋入式, 表面式}`（本部署实测出现过） |
| `simulated = None` | 其余 —— **未分类，显式标出来，不默认成实体** |

★★ 白名单而不是黑名单：黑名单（"不是仿真就是实体"）会把将来新出现的
`半实物仿真` 之类**静默当成实体资产** —— 正是这条溯源约定要防的事。
白名单的代价是多一行「安装方式未分类」。
★★ 守卫：**夹具里出现过的每一种 `install_mode` 都必须被分类**，
将来数据里多出一种会红，逼人来把分类写明确。

### ★★★★ 同一个缺陷在界面上又长了一次 —— 而且是从一个**看起来对**的决定里长出来的

`geo.html` 早先有一条决定：**没有几何数据的路段，在下拉框里禁用掉**，
并标上「无几何数据」。当时的理由是对的 —— 空壳图层画出来是一个永远空的画面，
看起来像 bug、实际是没数据，所以列出来并标明，比藏起来好。

**但它 `disabled = true` 了。** 后果是：**路段 1 根本选不中**，
而路段 1 上挂着 2 个断面。**那 2 个断面在界面上点不到。**

⇒ 刚刚从 spec 里删掉的那个「悄悄丢掉 2 个断面」，**换个地方原样长回来了**。
而且这次更难发现：spec 里丢的是数据，界面上丢的是**入口**。

**根因是一个范围错误**：「画不出这条路」是对**画布**说的，
不是对**这个路段的数据**说的。把两条不同的判断合成一个 `disabled`，
就顺手把第二条也一起否掉了。

**改法**：仍然列出来、仍然标「无线形数据」，但**不禁用**。
选中它时画布清空并说明原因，而断面面板**照常列出它的断面**——
每个都显示「算不出来」和理由。

★ 顺带把 T030 的验收也补齐了：断面面板逐个给出**来源徽标**，
`unavailable` 的那两个**不输出坐标**、只输出理由。
测试里有一条专门钉住这一点：`unavailable` 分支里**不得出现 `lat_deg`**，
并配了元测试（往那个分支里塞坐标，必须红）。

★★★★ **教训**：一条验收判据被修好，不等于它守护的东西就被守住了 ——
**同一个错误可以在规格、接口、界面三层各长一次**，而且每层长的样子都不一样：
规格里是丢数据，接口里是缺字段，界面里是**少一个能点的选项**。
修完一层要问：**这个错误还有别的地方能发生吗？**

### 为什么这一条比前两条更值得单独记

前两条计划外改动是「测试替身不像真的」「契约测试没有双向」——
都是**方法**层面的教训。
这一条是**需求文档自己在三节之内写下了互相矛盾的三句话**，
而三句话分开看每一句都清楚、都有理。
★★★★ **矛盾不在任何一句话里，在它们之间。** 只有把三句话摆在一起、
再拿实测数据对一遍，才看得见。

## Phase 3: User Story 1 - 桩号与经纬度互相算得出来，而且能核对 (P1) 🎯 MVP

**Goal**: 拿到桩号能算出经纬度，反过来也能；两者在米级以内闭合，
且**用一条真能失败的检查证明它是对的**

**Independent Test**: `curl` 一个已知桩号，得到经纬度，再算回去；
把 `crs.yaml` 的中央子午线临时改成 114，包围盒检查**必须失败**
（SC-008）。**不需要浏览器、不需要地图服务**

- [x] **T011** [US1] 在 `scaffold/modules/M6-api/app.py` 加
      `GET /v1/geometry/sections/{section_id}/geo`（桩号 → 经纬度）
      与 `GET …/geo/reverse`（经纬度 → 桩号）
      ★ 输出**必须带 `epsg`（4548）**，不得只写「39 带」——
      39 带有两个 EPSG 编码，取错东坐标差 **39,000,000 m**（FR-003）
      ★ 同时回带中间量 `x` / `y`：出错时能一眼看出是**几何**错了
      还是**投影**错了

- [x] **T012** [US1] 同文件加**越界拒绝**（FR-004）：
      桩号超路段范围 → 400；`section_id` 不存在 → 404；经纬度出带 → 422
      ★ **不得返回最近点、不得返回原点、不得返回空对象冒充成功**
      ★ 依赖 T011（同一文件）

- [x] **T013** [US1] 加 `GET /v1/geometry/sections/{section_id}/geo/route` 的
      **桩号域部分**（33 段的元数据：桩号区间、长度、半径、方位角、
      每段点列、`bbox`）

## Phase 5: User Story 3 - 沿线设施在地图上标得出来 (P3)

**Independent Test**: **原文**「3 个断面算出的经纬度全部落在 US1 给出的包围盒内」

> ### ⚠️ 这条判据与 spec 自身矛盾，**已改写**（详见下面「第三条计划外改动」）
>
> spec 的 Key Entities 说「线形单元 …… **地理坐标的唯一来源**」，
> Edge Cases 说「毕设 `K0+000` 与滨海 `K4635+000` 是**两个不同位置**」。
> 而实测：**路段 1 有 0 个线元、2 个断面；路段 6 有 33 个线元、1 个断面**。

> 它们的位置**不存在**，永远不可能落进路段 6 的包围盒。
> 「3 个断面全部落在包围盒内」**在原样写下时就是不可能满足的** ——
> 它只能靠**悄悄丢掉那 2 个断面**来"通过"。
>
> **改写后**：3 个断面**逐个**给出位置来源；`computed_from_station`
> 的那些必须落在本路段自己的区域帧内，`unavailable` 的那些必须给出理由、

## Implementation Strategy

### MVP First

**只做 Phase 1 + 2 + 3（T001–T019）= MVP。**

MVP 是一个**纯粹的计算能力**：桩号 ↔ 经纬度，加上七条判据
（SC-001 / 001b / 002 / 003 / 004 / 006 / 008）。
**它没有页面，且不需要页面** —— SC-007 明确要求它能在
没有浏览器、没有地图服务的环境里完整验证。
