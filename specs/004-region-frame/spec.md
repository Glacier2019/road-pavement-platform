# Feature Specification: 区域帧 —— 桩号与真实地理坐标的互算与呈现

**Feature Branch**: `004-region-frame`

**Created**: 2026-10-11

**Status**: Draft

**Input**: User description: "004 区域帧确定代号真实"

**前置条件（已于 2026-10-11 满足）**：003 的 spec 写明「区域帧另开 spec，
且必须等带号从'推断'变成'确认'」。用户已确认带号为**真实值** ——
3 度带 39 带 / 中央子午线 117°E / CGCS2000，`assumed: false`，**EPSG:4548**。
本 spec 的存在前提即此。

---

## 背景：区域帧要解决的到底是什么问题

003 做完的是**局部帧**：一条路自己的三维起伏，在一个局部米制坐标系里，
**不依赖任何大地基准**。它回答了「这条路长什么样」。

区域帧要回答的是另一个问题：**「这些桩号在地球上的哪里」**。

这个问题在本平台有一个硬约束：**全平台的定位只有一种语言 —— 桩号。**

实测（实库，不是规划）：

| 事实 | 值 |
|---|---|
| 有经纬度的表 | **只有 `monitor_cross_section.lat/lon`** |
| 那两列的实际填充 | **0 / 3 行有值**（全空） |
| `profile_ground_point` | **没有 lat/lon 列** |
| `alignment_element`（线形几何） | 33 段，**只有 x/y，没有经纬度** |

所以「桩号 ↔ 经纬度」这段换算**库里没有任何现成结果可以取**，
必须由投影正算现场得到。**这就是区域帧的第一件事**，也是它能成立的全部前提。

### 带号已确认，而且实测闭合

用 33 段线形几何的端点做高斯-克吕格**逆算**（CM 117°E / CGCS2000 / 东偏 500 km）：

| 检验 | 实测结果 |
|---|---|
| 正算→逆算往返（5 点，跨 116.5–120.34°E、24.5–26°N） | 最大偏差 **0.457 mm** |
| 33 段端点的经纬度范围 | **25.16789–25.20878°N，117.34292–117.37376°E** |
| 中心 | **25.18596°N / 117.35926°E** |
| 包围盒 | **4.552 km（南北）× 3.106 km（东西）** |
| 与 `crs.yaml` evidence 交叉核对 | 东偏推算 **+34.55 km**，evidence 独立写的是 **+34.6 km** ✓ |

★★ **坐标的读法已经确认：`alignment_element` 的 `x` 是北坐标、`y` 是东坐标**
（即 X=北 / Y=东，与 `crs.yaml` 的 `local_frame.axes` 同名同义）。
实测 `x` = 2784718.2..2789225.9（约 278 万米），`y` = 534559.2..537652.8
（约 53.5 万米）—— 这正是 `crs.yaml` evidence 里那条
「Y 值无带号前缀：实测 534559.2..537679.4 m」的**同一个数**。

★★★ **读反的失败形态是刺眼的，不是微妙的**：把 `x`/`y` 调换再逆算，
落点是 **4.54°N / 137.16°E —— 太平洋里，偏约 2300 km**。
这条要写成测试：读反必须产生一个**肉眼可见的荒谬结果**，
而不是一个看起来还挺合理的近邻。

### 现有数据的真实体量（决定了本 feature 能做什么）

| 数据 | 实有 | 对本 feature 的意义 |
|---|---|---|
| `alignment_element`（线形） | **33 段，全部属于「毕设」K0+000→K5+805.421** | **可以做**：路网骨架有真实几何 |
| `road_section` | 2 段（毕设 5.805 km；滨海大通道 K4635+000→K4654+701） | 毕设有几何，滨海**一段都没有** |
| `road_line` | 5 条，其中 3 条（`TEST-PRJ-*`）**0 个路段** | 空壳，不该画出来 |
| `monitor_cross_section` | 3 个断面，lat/lon **全空** | 位置由桩号算出 |
| `disease_record` | **0 行** | ★ **病害分布做不了** |
| `media_file` | **0 行** | ★ **影像做不了** |

> ★★★ **003 把区域帧的范围记为「路网、病害分布、DEM、影像底图」。
> 但其中两项一行数据都没有。** 给两张空表写界面，等于规格一开始就注定做不出东西 ——
> 而且做出来的是**一个永远空的图层**，看起来像 bug、实际是没数据。
> 所以本 spec 把它们**显式排除**（见「不做什么」），等有数据再各开一个 spec。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 桩号与经纬度互相算得出来，而且能核对 (Priority: P1)

测绘/设计人员拿到一个桩号（例如 `K2+900`），需要知道它在
**真实地理坐标**里的位置；反过来，拿到一个经纬度，需要知道它对应哪个桩号。
现在这两件事在平台里**一件也做不到** —— 库里的经纬度列是空的。

**为什么是 P1**：这是区域帧的**全部前提**。没有它，路网画不出来、
断面标不上去、任何底图都贴不上。而且它**不依赖任何前端** ——
是一个纯计算能力，可以在没有地图、没有浏览器的情况下被完整验证。

**Why this priority**: 它是唯一一个「有数据 + 有明确对错 + 可以离线验证」的部分。

**Independent Test**: 取一个已知桩号，算出经纬度，再用正算回到桩号；
两者必须在米级以内闭合。手工用一个独立的投影工具核对同一个点。

**Acceptance Scenarios**:

1. **Given** 毕设路上的桩号 `K2+900`，**When** 请求它的经纬度，
   **Then** 返回一个落在 **25.16–25.21°N、117.34–117.38°E** 范围内的点，
   且该点**明确标注所用的带号与 EPSG 编码**。
2. **Given** 上一步返回的经纬度，**When** 反过来请求它的桩号，
   **Then** 回到 `K2+900`（误差 ≤ 1 m）。
3. **Given** 一段线形几何的两端，**When** 两端都做逆算，
   **Then** 算出的方位角与该段的 `azimuth_deg` 在 0.5° 以内一致。
4. **Given** 一个落在路线范围之外的桩号（如 `K9+999`），**When** 请求换算，
   **Then** **明确报错说超出范围**，绝不返回一个"最近点"或原点。

### User Story 2 - 在真实地理坐标下看到路网骨架 (Priority: P2)

打开一个页面，能看到毕设路 **5.8 km 的走向**画在真实经纬度上，
包含 33 段线形（直线/圆曲线/缓和曲线用不同画法区分），
并且能点一段看到它的桩号区间、长度、半径、方位角。

**Why this priority**: 它是 US1 的第一个消费者，也是"区域帧"这个名字的直观兑现。
但它**依赖 US1**，且需要前端。

**Independent Test**: 页面上量取首末两点的经纬度，与 US1 算出的值一致；
用一条已知是圆曲线的段落，目视核对其弯曲方向。

**Acceptance Scenarios**:

1. **Given** 页面已加载，**When** 查看整体视图，**Then** 路线的**长宽比**与
   实测包围盒（4.55 km × 3.11 km）一致，**没有把南北和东西弄反**。
2. **Given** 33 段线形，**When** 渲染，**Then** **圆曲线段是弯的** ——
   不能把每段都画成直连两端点的折线。
3. **Given** 点击任意一段，**Then** 弹出它的桩号区间、长度、半径、方位角。
4. **Given** 3 条 0 路段的 `road_line`（`TEST-PRJ-*`），**Then** 它们
   **不出现在图上**，或明确标为"无几何数据"。

### User Story 3 - 沿线设施在地图上标得出来 (Priority: P3)

3 个断面（含仿真设备所在的 `K2+900`）应该能在图上看到它们的真实位置。

**Why this priority**: 有了才知道设备装在哪。但它的位置**全部来自 US1 的换算**
（lat/lon 列是空的），所以它纯粹是 US1 的一个应用。

**Independent Test**: 3 个断面算出的经纬度，必须落在 US1 给出的路线包围盒内。

**Acceptance Scenarios**:

1. **Given** 3 个断面，**When** 显示位置，**Then** 位置**由桩号算出**，
   且在图上标注了"位置由桩号换算得到，库中经纬度列为空"。
2. **Given** `K2+900` 上的仿真设备，**Then** 它与真实设备**在视觉上可区分**
   （延续 `SIMWIM01` 这条溯源约定）。

### Edge Cases

- **`x`/`y` 读反** → 落点必须在太平洋；换算能力必须把它挡住（见背景一节）。
- **带号前缀混淆**：`EPSG:4548`（无前缀，东偏 500000）与 `EPSG:4527`
  （有前缀，东偏 39500000）**不可互换**，取错东坐标差 **39,000,000 m**。
  输出必须**显式带上 EPSG 编码**，不能只写"39 带"。
- **跨带**：路线经度 117.34–117.38°E，距中央子午线 117°E 仅 0.34–0.38°，
  **完全落在 39 带内**（3 度带半宽 1.5°）。但换算能力**仍须检查**
  输入是否落在本带，超带要报错而不是硬算。
- **两个路段桩号语义不同**：毕设 `K0+000` 与滨海 `K4635+000` 是**两个不同位置**。
  桩号换算**必须同时给定路段**，否则 `K0+000` 是歧义的。
- **空经纬度不能当成 0,0**：`monitor_cross_section.lat/lon` 全空，
  若把 NULL 读成 0，3 个断面会一起堆在几内亚湾外的 (0°,0°) 而**不报任何错**。
- **超出桩号范围**：见 US1 场景 4。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供「桩号 → 经纬度」的换算能力，
  **输入必须包含路段**（桩号单独出现是歧义的）。
- **FR-002**: 系统 MUST 提供「经纬度 → 桩号」的反向换算。
- **FR-003**: 换算结果 MUST 同时携带 **EPSG 编码**（`4548`）与带号（39 带），
  **不得只写"39 带"** —— 两个 EPSG 编码的差别是 39,000 km。
- **FR-004**: 系统 MUST NOT 在桩号超出该路段范围时返回结果，
  必须明确报错。**不得返回最近点、不得返回原点、不得返回空对象冒充成功。**
- **FR-005**: 换算所使用的带号 MUST 从 `crs.yaml` **读取**，
  **不得写死在代码里**；且 MUST 在 `assumed: false` 与 `assumed: true` 两种状态下都能工作
  （前者照常用，后者照常用但在界面或日志里标注"值是推断的"）。
- **FR-006**: 系统 MUST 能渲染 33 段线形几何，且 **圆曲线段必须按曲率画成弯的**，
  不得退化成首末点直连。
- **FR-007**: 渲染 MUST 保持真实比例与真实方位
  （南北与东西**不得互换**，长宽比不得失真）。
- **FR-008**: 系统 MUST NOT 渲染 0 路段的 `road_line`（`TEST-PRJ-*`）。
- **FR-009**: 3 个断面的位置 MUST 由桩号换算得到，
  且 MUST 在界面上标注"位置由桩号换算"这一事实。
- **FR-010**: 系统 MUST NOT 把 `NULL` 经纬度当作 `(0, 0)`。

### Key Entities

- **路段（road_section）**：桩号的命名域。换算的必要输入之一。
- **线形单元（alignment_element）**：33 段，带 `start_x/start_y/end_x/end_y`、
  `azimuth_deg`、`radius_start_m/radius_end_m`。**地理坐标的唯一来源。**
- **断面（monitor_cross_section）**：3 个，带桩号；经纬度列为空，位置由换算得到。
- **坐标基准配置（crs.yaml）**：带号、中央子午线、椭球、EPSG 编码的唯一出处。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 本 feature 的「桩号→经纬度」，其平面坐标部分须与**已验证的实现**
  `adapters.geom.point_at` **一致**（该实现 steps=64 时实测误差 < 1e-9 m），
  加上投影后的合成结果偏差 **≤ 1 m**。
  ★ **这一条比"往返闭合"强**：正算与反算按构造互为逆运算，
  往返闭合只证明二者自洽 —— **中央子午线取错一整带也能完美闭合**。
- **SC-001b**: 「桩号→经纬度→桩号」往返闭合 ≤ 1 m。
  ★ **只作为必要条件保留，不得单独作为判据**（理由同 SC-001）。
- **SC-002**: 33 段端点算出的经纬度，**全部落在
  25.16–25.21°N / 117.34–117.38°E** 之内；中心与实测
  25.18596°N / 117.35926°E 相差 ≤ 200 m。
- **SC-003**: 线形两端的方位角与 `azimuth_deg` 相差 **≤ 0.5°**。
- **SC-004**: 把 `x`/`y` 故意调换后，算出的纬度 **< 10°N**
  —— 即失败形态**肉眼可辨**，不会伪装成一个合理的近邻。
- **SC-005**: 渲染出的路线长宽比与实测包围盒（4.55 × 3.11 km）
  相差 **≤ 1%**，且**南北、东西不互换**。
- **SC-006**: 输入超范围桩号时，**100% 报错**，无一例返回看似成功的值。
- **SC-007**: 换算能力在**没有浏览器、没有地图服务**的环境里可以完整验证。
- **SC-008**: ★ **SC-001 与 SC-002 的对照**（宪法 Principle V：新增检查必须配元测试）——
  把中央子午线**故意取错一整带**（117°E → 114°E）时，
  SC-002 的包围盒检查**必须失败**。
  若它仍然通过，说明这两条判据量不到它们声称在量的东西。

## 不做什么（显式排除，各附理由）

| 项 | 理由 |
|---|---|
| **病害分布图层** | `disease_record` **0 行**。没有数据，做出来是一个永远空的图层 |
| **影像底图 / 实景照片图层** | `media_file` **0 行**。同上 |
| **在线地图底图（含高德）** | ★ **2026-10-10 已决定：不用高德**，也不用任何在线瓦片。理由与实测见 `specs/003-…/research.md` |
| **瓦片服务 / 切片金字塔** | 路线包围盒仅 **4.55 × 3.11 km**，z=13 只需 2×3 块瓦片、z=16 也只需 7×10 块。延续 003 的结论：**整幅一次取完比切片服务简单** |
| **DEM 高程底图** | 003 已用真实 CRG（0.1 m 分辨率）表达起伏，比任何公开 DEM 都精确 |
| **`cross_section_ground_point` 建三维** | 003 已排除：密度（每断面 4 点）不足以建三维 |
| **M9 直连数据库取几何** | 宪法 Principle II：M9 **拿不到 `PG_DSN`**。几何必须经 M6 API 取 |

## Assumptions

- 带号是真实值 —— 由用户在 2026-10-11 确认。**这不是设计方 `.PRJ` 的结论**，
  确认来源须如实记录（`assumed: false` 的出处是平台负责人的决定）。
- `alignment_element` 的 `x` 是北坐标、`y` 是东坐标 ——
  由实测范围（x 约 278 万、y 约 53.5 万）与逆算落点（闽中）共同确认。
- 毕设路是区域帧的**唯一**有几何的路段。滨海大通道的几何将来由设计文件导入补齐，
  本 spec 不为它造数据。
- 换算能力属于 M6 API（数据出口），不属于 M9（宪法 Principle II）。

## 待澄清

以下问题**不影响本 spec 现在开工**，但会影响 plan 阶段的选择：

1. **底图到底用什么**：003 定了"不用高德、也不用在线瓦片"，
   但"那么用什么"还没定 —— 自烘一张影像、纯矢量线框、还是干脆无底图只画路线？
2. ✅ **已定（2026-10-11，用户裁决）：自包含 HTML，放 M9，不用 CesiumJS（方案 A）。**
   依据 ——

   003 的 `plan.md` 曾写「M8-apps 不动（CesiumJS 留给区域帧）」，但那是**未评估**的
   一句话。评估结果：

   - ★ **仓库里已有一条测试挡着它。** `tests/contract/test_console.py` 断言 M9 每个
     页面**不得出现带 `https?://` 的 `<script src>` / `<link href>`**，而该断言的注释
     写明：**它当初正是为挡 CDN 版 three.js / CesiumJS 写的**。用 CDN 引 CesiumJS
     **现在就会红**，不是新增限制。
   - 不用 CDN 就得把整个库烘进仓库：**大于 4 MB** 加配套静态资源，会推翻 003 的
     「自包含、无构建步骤、无新依赖」。
   - 量级不对：CesiumJS 是**全球尺度的三维地球引擎**，而本 feature 只有
     **5.8 km / 33 段**。003 的 `sim.html` 已在 962 行里做完网格解码、三维显示与曲率。
   - M8-apps 的 README 自述「**状态：骨架**……**业务逻辑未实现**，接口返回 **501**」
     ⇒ 放那里等于先新建一个应用模块；而 M9 已有 5 个页面的先例。

   ⇒ 页面落 **M9**，延续 003：**自包含 HTML（内联脚本与样式）、无构建步骤、无新依赖**。
3. ✅ **已定（2026-10-11，用户裁决）：保留 1 m，另加真能失败的检查（方案 A）。**
   已落实为 spec 的 SC-001（对齐已验证实现）、SC-001b（往返，仅作必要条件）、
   SC-008（取错子午线时 SC-002 必须失败）。
   以下是作出该裁决的依据 ——

   SC-001 定 1 m。★ 初稿写的理由是"余量留给桩号采样精度"，
   **这个理由已被实测推翻**；1 m 的真正作用是**逼几何画对**（见第 4 条）。

   ★★ **这条链上有四个不同的精度量，不能混为一谈：**

   | 环节 | 实测误差 | 谁做的 |
   |---|---|---|
   | **线元恢复** 桩号→(x, y) | **< 1e-9 m**（steps=64）；实测残差 **3.2×10⁻⁸ m** | `adapters/geom.point_at`，**已实现已验** |
   | 投影换算 (x, y)→经纬度 往返 | **0.457 mm** | 本 feature 新写 |
   | 桩号存储 | **1 mm**（6 位小数） | 数据库 |
   | 弦化简化 | **12.588 m** / **1.736 m** | ✗ 会被 1 m 挡住 |

   线元恢复委托论文 §2.2 那套：`∫(cosθ, sinθ) ds` 走复合 Simpson，
   **方位角精确、只有积分是数值的**；缓和曲线是 Fresnel 积分、无初等闭式。
   ⇒ **1 m 比实际实现松约 3×10⁷ 倍，是下限而非精度描述。**

   ★★★ **SC-001 原写法有缺陷，已按方案 A 改。** 原写「桩号→经纬度→桩号 往返闭合 ≤ 1 m」，
   而正反算按构造互为逆运算 —— **中央子午线取错一整带，往返照样完美闭合**。
   这就是宪法 Principle V 说的「一个永远不会失败的检查，比没有检查更糟」。
   改法见上文 SC-001（对齐已验证实现）、SC-001b（往返降为必要条件）、
   SC-008（取错子午线时 SC-002 必须失败的对照）。

4. ★★★★ **设计坐标指向的位置，与设计者自己的地形对不上 —— 这是本 spec 最大的未决问题。**

   实测（2026-10-11）：

   | 项 | 值 |
   |---|---|
   | 起点设计坐标 | `2789225.87567849 / 534559.21792837`（`.JD` 里写了 8 位小数） |
   | 逆算落点 | **25.209°N / 117.36°E**（戴云山区） |
   | 同点 SRTM 真实地形 | **511 .. 1304 m**，5.5 km 内高差 838 m（平均纵坡约 15%） |
   | **设计者自己的地面线**（`.DMX`） | **46.4 .. 124.2 m**，高差 77.8 m（平均纵坡 **1.3%**，平原微丘特征） |
   | 两者**形状相关系数** | **r = −0.144**（若只是基准面不同，应接近 +1） |
   | 两者均值差 | **+825 m** |
   | 设计文件是否声明坐标系统 | **`.PRJ` / `.CTR` / `.pm` 三份都没有** |

   ★ `.DMX` 首行 `0.000 → 57.262000` 与实库 `profile_ground_point[0] = 57.2620`
   **逐点完全一致** ⇒ 数据库忠实导入了设计者的数据，**不是导入环节出的错**。

   ⇒ **两者必居其一**：坐标是局部/自定的，或者地面模型是生成的。
   本实测**只能证明二者不一致，不能判定是哪一种**。

   **对 004 的影响**：桩号→经纬度的**算术**已被证实（往返 0.457 mm），
   但它的**地理含义未获独立佐证**。任何真实底图都会替一份未经证实的位置断言背书。

   **影响范围**：003 的带号由用户确认为真实值（`assumed: false`），
   这是**平台负责人的决定**，数学上仍然成立、不必推翻；
   但"这条路在闽中"这句话，目前**只有坐标本身作证，而设计者的地形反驳它**。
