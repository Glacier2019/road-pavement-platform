# 工程决策记录

记**为什么这么定**，不记「做了什么」（那在 spec / tasks / 代码注释里）。
一条决策在这里，通常意味着它**反直觉**、或者**曾经选错过** ——
所以每条都要能回答：「不这么定会怎样？」

判定口径：宪法 §VI「通用商业化优先」。**自证不算证据** ——
凡是写「已实现」的，必须附一条能被别人复跑的判据；只有主张没有判据的，在这里写「未验证」。

## D-001 坐标基准的**权威**在库里，`crs.yaml` 是派生产物

**决定**：`design_project` / `road_section` 两张表的 `crs_*` 列是唯一权威；
`modules/M9-console/config/crs.yaml` 由 `tools/export_crs_yaml.py` 从库里生成。

**为什么不反过来（YAML 为准）**：
YAML 只能表达「一个平台一个基准」。005 的整个目的就是**多项目多路段共存** ——
两个项目两套中央子午线，同一个桩号必须算出两个不同且都正确的经纬度。
一个单例配置文件表达不了这件事；硬要做就得为每个项目开一个文件，
那已经是「用文件系统模拟一张表」，而且**外键、非空、唯一性一个都没有**。

**代价（必须承认）**：文件与库会漂。
⇒ 所以配了**三道检查**，且都实测过会叫：
- `m9-集成面` / `GET /v1/crs/drift`：文件 vs **契约值**（M9 经 `/gw` → M6 → M3，**不碰库**）
- `quickstart_probe.py` 判据 2b：文件 vs **库**（唯一能比全五个字段的通道）
- 产物的 `generated_from` 块自述出处（改了哪一行、哪个字段跟哪一行比）

**★ 一项未验证的**：`crs_evidence` 走不了契约通道（M6 的 HTTP 响应里没有这个字段），
所以漂移检查把它报成 **`skipped`（未比对）**，**不是通过**。
「通道没有这个字段」和「值不一样」是两件事，不许混成一句「一致」。
是否给它加一个契约字段，**尚未决定**。

## D-002 两级都有值时必须**相等**，不等直接报错

**决定**：项目级和路段级都填了 `crs_epsg` 且不相等 ⇒ 写入被拒。
这是 data-model E2 五态里**唯一被拒**的一态。

**为什么不是「路段优先」**：真实的趋势累积误差 ——
一条长路线跨 3° 带边界时，规范做法是**整条线用一个中央子午线**，
分段换带会让交接处出现无法闭合的错台。所以「路段级 ≠ 项目级」
在实践中几乎总是**录入错误**，不是需求。把它做成静默优先级，
等于让一个录入错误变成一条悄悄偏移的路线。

**代价（必须承认）**：如果有一天真的要跨带，**得先改这条规则**，不能绕。
⇒ 记录下来，而不是等它发生时才争论。

**★ 只拦第 ② 态**。态①③④⑤ 一律放行 —— 守卫**只拒绝，不填充、不代选**。
③（项目有、路段空）取项目；④（项目空、路段有）取路段，`crs_source=section`；
⑤（都没有）是**有类型的「没有」**，读路径给 503 —— 不是回落到默认带号。

## D-003 `spatial_ref_sys` 只做**校验**，不做业务表

**决定**：外键指向 `spatial_ref_sys(srid)`；该表不进 `ALL_TABLES` / `CROSS_TABLES` /
`TABLE_OWNER`，唯一入口是 `GeRepository.srid_exists()`；整库计数类测试**排除**它。

**为什么**：它是 PostGIS 的元数据表（8500 行），不是业务模型的一部分。
把它算进「本库有多少张表」，会让每一次 PostGIS 升级都让交付物口径失效。
而它又**必须**被引用 —— 否则库会接受任意整数当 SRID。

**★ 一条被证伪了、不要写进代码的规律**：
`SRID = 带号 + 4509`（39 带 → 4548）对 25–45 带实测 **21/21 无反例**。
但它**只对 3 度带族成立**。同样被证伪的还有两条：
`crs_central_meridian_deg == crs_zone_number * 3`（4524 是反例）、
以及「`+lon_0` 是通用的」——`utm` 与 4326 的 `proj4text` 里根本没有它。
⇒ **只有 SRID 本身是通用的**。带号、中央子午线都是它的派生物，
不许当成可与它并列的独立真相，更不许写成 DDL 的 `check`。

## D-004 迁移**从不自动执行** —— 所以守卫不能只写在迁移里

**决定**：装库守卫放在 `sql/25_crs_two_level_guard.sql`，
由 `docker-compose.skeleton.yml` 挂进 `/docker-entrypoint-initdb.d/`。

**为什么**：`10_ddl_v0.6.sql` / `20_partitions.sql` / `90_seed_skeleton.sql` 是
全新装的唯一真相，`85_`–`99_` 那些迁移**一次都不会被自动跑**。
一个只写在迁移里的守卫，对**每一个全新装**等于不存在 ——
而文件在、代码也「做了」，**谁都看不出来**。
这与 004 踩的是同一个坑（见 D-005），只换了个对象。

**★ 顺带证明了一个更硬的道理**：
「挂进去了」这句话，只有**真的起一个全新装跑一遍**才算说过。
实测第一次的结果是 `Permission denied` → **initdb 整体中止、容器直接退出**。
根因：文件由 `write` 创建时 mode 是 `600`，
而 postgres 容器以 `postgres` 用户跑，读不了。
⇒ 不可读**不是「少了守卫」，是「全新装起不来」**。
`git` 只记录可执行位，`git ls-files -s` 里全是 `100644`，
所以**仓库是好的、clone 出来也是 644**，坑只在本地工作区 ——
偏偏又是跑全新装的那一份。⇒ 判据 §18h。

## D-005 005 实测撞出来的**五类「假绿」**，都补了守卫

这一节是本文档存在的**主要理由**：这五类都不是靠读代码能发现的。

| # | 假绿的样子 | 真相 | 现在的守卫 |
|---|---|---|---|
| 1 | 迁移/种子写了，以为会跑 | **从不自动执行** | `25_` 挂进 initdb.d + §18g 断言「真的会被跑到」 |
| 2 | `98_` 后记③ 说「两级一致检查交给写入侧」 | **没有任何任务接住** ⇒ 不变量压根不存在，实测 `UPDATE 1` 成功 | `25_` 守卫 + 判据 2c（含 DROP-TRIGGER 元测试）+ T047 |
| 3 | 手维护的 `Dockerfile` COPY 文件清单 | 漏一个文件 ⇒ 一个端点 500，**而健康检查是绿的** | `COPY *.py` / `COPY *.html` + 能识别 `*.ext` 的覆盖判据 |
| 4 | 「不得连库」只扫 `app.py` 一个文件名 | 守的是「当时想到的那一个」，不是「结构」 | 清单 + **清单完整性检查**（当场抓出 `gaps.py`）+ 元测试 |
| 5 | 一个数字写进文档当成判据 | 数字必然过期，而**没有任何检查在读它** | 判据改成「失败 0 且跳过 0」；宪法里的「12/12」已修为实况 |

★ 配套的三条方法论，也都在 005 里各踩过一次：
- **一个「必须失败」的步骤，如果从没被执行过，那是假设，不是验证。**
- **一个只会红不会绿的检查，不算通过** —— 两个方向都要试。
- **一个在已经坏掉的数据上装上去的守卫，表现是永远绿** ⇒
  装之前先查有没有既存矛盾，有就当场拒绝。

## D-006 守卫是**一份定义、两条执行路径**，不是两份

**决定**：`25_crs_two_level_guard.sql` 一个文件，
既被 initdb 挂载（全新装），也能手动 `psql -f` 跑（已有的库）。幂等。

**为什么不写成两份**：两份定义会漂，而**漂掉的那一半不会报错** ——
它只是**少拦一种情况**。那种失效没有任何症状，直到脏数据出现。

★ 推广：**同一条性质，一份定义一个负责人。**

「M9 镜像清单」这一条性质，删掉重复的那份时留了指针，没留副本。

## D-007 手写投影的**准**由外部标尺定义，**能算什么**由投影族定义

**决定（两件事，一起定）**：

1. **准不准**（T038–T042）：拿 PostGIS 的 `ST_Transform` 做独立对拍。
   三点（起点 / 中点 / 终点），容差 **1e-4 m（100 µm）**。
2. **算不算得了**（T043–T044）：`geo.py` 声明 `IMPLEMENTED_FAMILIES = {"tmerc"}`；
   族不在列 → 抛 `CrsError` → 接口 **503**，消息里同时说出 **SRID 和族**。

**为什么「准」必须用外部标尺**：
在这条判据之前，「投影是准的」的**全部**证据是正算 → 反算 → 回到原点。
而往返闭合只证明 `forward` 与 `inverse` **互为逆运算**，
**不证明它们都对着同一个正确的投影** —— 两个函数一起偏，往返照样闭合，
而且闭合得一样漂亮。这与「跑一遍自己的测试全绿」是同一种自证（§VI ③）。
★ PostGIS 里的 PROJ 是「别人写的、没参与过这段代码」的实现。

**实测（2026-10-13，`§19`）**：north 最大 **9.246 µm**、east 最大 **0.001 µm**。
★ 两种差**性质不同**：north 的 9 µm 是**系统性**的（两边幂级数截断阶数不同，
三点差值几乎一致：9.155 / 9.195 / 9.246 µm，随纬度缓慢变大）；
east 的 0.001 µm 是**浮点噪声**。
⇒ 把 9 µm 当噪声调容差会调不出结果；把 0.001 µm 当精度去写宣传，是把噪声说成成绩。

**容差为什么取 1e-4 m**：比实测基线宽约一个数量级。
**不许取 1e-9**（拿浮点噪声当判据，判据会随机红，然后被人放大容差，
连「真的偏了」一起放过）；**也不许取 1e-2**（等于说偏 1 cm 没关系，
而 1 cm 在路面放样里有关系）。

**为什么「能算什么」要单独声明**：
数据模型按宪法 §VI **接受任意 SRID** —— 这是对的，通用产品不该被实现限制入库。
但手写换算**只实现了高斯-克吕格**。两者合起来的旧行为是：
`crs_epsg` 填成 `2154`（Lambert，`+proj=lcc`），代码**不报错**，
把 Lambert 的参数当高斯-克吕格算，**输出一个量级正常、位置错掉几百米的坐标**。
★★ 这是 004 那条教训的形状 ——「**看着正常的错值比缺失更危险**」：
缺失会被发现（503 / 空值 / 报错），错值不会，它会一路流到放样桩上。

**为什么不写「支持哪些 SRID」的白名单**：
白名单要手维护，加一个带号就得改代码；而且它**会漏** ——
漏掉的那个 SRID **不报错**，它只是**不做检查**（与 §4 那份「文件名单」同一种失效）。
族是 PROJ 自己维护的客观事实（`+proj=`），`4548` 与 `4524` 同族，列两遍就是两份会漂的真相。
⇒ **只声明族，不声明 SRID。**

**为什么是三层分工，不是全放 `geo.py`**（宪法 §II：读只经 M3）：
| 层 | 做什么 | 为什么是它 |
|---|---|---|
| `M3-rpdao/repo.py` `crs_family(srid)` | 从 `spatial_ref_sys.proj4text` 取族 | **只有它有连接** |
| `M6-api/geo.py` `require_family()` | 声明自己实现了哪些族，不在列就拒 | **它零数据库**（T003 实测） |
| `M6-api/app.py` | `CrsError` → 503，并补上 SRID | 只有它知道 HTTP |

★ 族是**客观事实**，「支持」是**某个实现的属性** —— 所以它们属于不同的层。
M3 不判「支持不支持」，否则改 `geo.py` 支持的族还得回来改 M3。

**「不声明族」也报错，不放行**：
放行等于说「没告诉我族 = 我算得了」。**「不知道」和「支持」必须分开** ——
前者不是通过的证据。
★ 与宪法 §VI ②的关系已对过：那一条说的是「国际标准标识符为权威，
**本地记法**可空；可空字段缺失时 MUST NOT 报错」。
`projection_family` **不是本地记法**，它是 `+proj=` 的派生物，不适用。
★ 而真正会缺的那个（EPSG 本身，`assumed: true` 时）——
  那条路径由 `_geo_crs` 显式**声明** `tmerc`（假定值只用带号+中央子午线表达，
  而那套表达就是高斯-克吕格），所以也不是「不声明就放行」。

**`projection_family` 故意不写进 `crs.yaml`**：
文件里已经有 `epsg_after_confirm: 4548`，族由 SRID 唯一决定。
再抄一份就是**同一件事的第二个真相来源**，而两者会漂
（改了 SRID 忘了改族，文件就自相矛盾）。且 M6 已不读该文件（D-001）。
★ **两份真相里，漂掉的那一份不会报错。**

## D-008 宪法**加了原则**，而**没有任何东西会因此变红** —— 已补守卫

**背景**：重跑 005 的 Constitution Check 时，发现宪法 1.1.0 新增的**原则 VI
根本没进过这张表**。查下去，三个问题叠在一起：

| # | 问题 | 后果 |
|---|---|---|
| ① | 原则 I–V 用 `###`，VI 用 `##` | 按 `###` 找原则的东西**看不见第六条** |
| ② | `plan-template.md` 的门禁表位置只写着 `[Gates determined based on constitution file]` | **一个不列原则的占位符** ⇒ 新原则不会在任何 plan 里产生新行 |
| ③ | `scaffold/tests/` 里**零命中** `.specify/` | 宪法、模板、每份 plan 的检查表**全是无人读的文档** |

**判断**：这不是「一次忘记同步」。**它是一个结构**：新原则进来，
产生它的地方（宪法）和被消费的地方（模板 / plan）之间**没有任何连接**，
而缺失是**沉默**的 —— 没有任何检查会注意到少了一行。

★★★ 换个说法：这正是原则 V 说的东西。「一个永远不会失败的检查，比没有检查更糟」——
只不过这里的「检查」是**一份没人读的检查表**。它比没有检查更坏：
**它让人以为已经考虑过了。**

### 决定

1. **宪法**：`## VI.` → `### VI.`，升 **1.1.1（PATCH）**。
   ★ 按 Governance，PATCH = 措辞澄清 / **非语义调整**。六条原则的**要求**一条没变，
   变的是「它们会不会被人看见」。**规范性内容一字未动。**
2. **`plan-template.md`**：占位符换成**逐条列出六条原则**的空表。
   ⇒ 以后新增原则，模板必须跟着改，而那是一次**看得见的编辑**。
3. **`spec-template.md`**：新增「通用性与商业化」一节（原则 VI 的三问）。
4. **新套件 `test_spec_kit_consistency.py`**（`PY` 桶，纯文本、离线）。
5. **`005/plan.md`** 两张 Constitution Check 表补 VI 行，并把重跑结论写进去。

### ★★ 写这个套件时最重要的一个决定：**检查者不许有被检查者的盲区**

最自然的写法是 `re.compile(r"^### ([IVX]+)\. ")`。
★ 而它会在**原则 VI 隐形的那整段时间里全绿** —— 因为「看不见第六条」正是当时的 bug。
检查者复刻了被检查者的盲区，于是它证明的不是「六条都在」，
而是「**按我的找法找到的都在这**」。

⇒ 两条措施：
- 找法写成 `#{2,4}`（**先找全**），层级一致性**单独判**（`§1` 两项分开报）；
- `§1b` 元测试故意把层级改坏 → 断言「**仍然找得到六条**，但一致性必须变红」。

### ★★ 第二个决定：001–004 **显式登记，不静默豁免**

001–004 的 `plan.md` 里 Constitution Check **表体是自由格式**，没有逐原则的行 ——
它们写于模板不列原则的年代。**不能拿今天的模板去判它们罚**，
但那也**不等于它们合规**。

⇒ 在套件里显式登记（`_LEGACY_NO_PRINCIPLE_ROWS`，带理由），并断言**这份名单只许缩短**：
某个 feature 补上了逐原则的行，`§3c` 会主动把「该删的」指出来。

★★ 静默跳过四份历史 plan，就是这个仓库反复栽的那一类错
（「一个只扫一个文件名的名单」）。**这里不重复它。**

### ★★ 第三个决定：顺带把「不许写死套件数」变成判据（`§5`）

这次重跑又撞见同一个老毛病，且**到处复发**：宪法 §I（「当前 N 套件」）、
宪法工作流第 1 条（「通过 N ｜…」）、005 plan 的 Testing 行、
001 的 SC-005、001 / 004 的 quickstart 期望 —— **全是同一句话里的自相矛盾**：
一边写死一个数字，一边声明判据不是这个数字。

⇒ `§5` 扫**规范性文档**（宪法、模板、各 feature 的 plan / spec / quickstart），
出现写死的套件数 / 通过数即红。
★ 配双向元测试：**4 种真实复发过的写法必须全部抓住**，
且「`21/21 无反例`」「`0/3 行有值`」「`332/332 桩号`」**不得误伤**。

**刻意不扫** `research.md` / `tasks.md` / `工单-*.md` / `checklists/` / `scaffold/` 说明文档：
那些是**带日期的历史记录**（「2026-10-11 实测通过 N」）。
把当时的事实改成今天的事实，等于**篡改记录**。
⇒ 这个取舍是**刻意的，不是漏扫**（套件里的注释写明了）。

### 代价（如实记）

- 001–004 的 plan **没有**因此合规。它们仍缺逐原则的行，
  只是**从「没人知道」变成「被登记着、且只会变少」**。
- `§5` 只认**四种已见过的写法**。换一种花样（比如「全绿 22 条」）它抓不住。
  ★ 这是一条**模式匹配**的检查，不是语义检查 —— **边界就在这里**。

## D-009 两份**手写的清单**，而没有任何东西在读它们

**形状**（与 D-008 同一条线，换了对象）：

> A 声明了要去消费 B。那份清单是**手写的**。
> 于是「新增一个 B」不产生任何信号 —— **不报错，也不会红。**

D-008 守的是「宪法加了原则 → 模板与 plan 该产生新行」。
本次顺线扫，扫出**两处**同样的失联，以及**两条我编错了的规则**。

### 一、扫出来的两处

### 二、我编错了的两条规则（如实记下来）

补守卫时我先写了 §2c：「每个 `_migrate_` 文件里必须有结构变更语句」。
**第一次跑就报红** —— 而红的是**规则**，不是文件：

> `90_migrate_v05_batch_remark.sql` 头部自己写着
> 「依赖：无（**纯数据订正，不动表结构、不动任何列**）」。

⇒ **`_migrate_` 完全可以是纯数据迁移。那条规则编码了一个假前提。**

又试了三条替代，**实测全不成立**：

| 候选判据 | 实测 |
|---|---|
| 头部声明「目标库 / 幂等 / 依赖」三行 | 14 个迁移里只有 **1** 个齐备 |
| 头部自述「迁移 NN」 | 迁移 **6/14**、种子 **0/3** |
| 有统一的迁移执行器 | **没有**（迁移是人手工跑的） |

⇒ **「该是迁移还是种子」没有可靠的机器判据。**
所以 §2c 不判定它，只做两件**真的**能查的事：
把三类的规模打出来（`4 ＋ 14 ＋ 2 == 20`，一个精确的划分），
以及「**每个 sql 总得做点什么**」（与文件名无关）。

★★ **教训：一条编码了错误规则的检查，比没有检查更糟。**
它会把正确的东西报成错的，然后逼你去改那个**正确的东西**。

### 三、决定

1. **新建 `tests/contract/_env.py`**：`.env` / DSN 解析收成**一份**。
   本仓原先有 **4 份**基本等价的实现（都踩过并补上了"行内注释"那个坑），
   而**唯一不读 `.env` 的那份，恰好就是唯一没人跑的那份**。
   ★ 已有 4 份**暂不改动**：它们的**取默认值策略不同**
   （baseline 用默认值，query 要求四键齐全否则 None）——
   统一策略是另一件事，需要单独决定，不顺手改。
2. **`test_geometry_solver.py` 改为 `import _env`**，并补登记进运行器（`DAO` 桶）。
   补登记之后第 5–8 组**全部跑起来**，全绿（332 vs 332、可重建、篡改必被发现）。
3. **新建 `tests/contract/test_runner_completeness.py`**：守两份清单的完整性。
   - §1 每个 `tests/**/*.py` 要么登记、要么在豁免表里写明理由；
   - §2 每个 `sql/*.sql` 要么挂载、要么是迁移、要么在豁免表里写明理由；
   - §1b/§2b **三条元测试**（拿掉一行登记、拿掉一行挂载、拿掉一个种子的挂载）；
   - §3 豁免表**只许缩短**，且理由 MUST 指向证据（不许只写「这是有意的」）。
4. **`tests/README.md`** 记下 `_env.py` 这个约定，免得再长出第六份。

### 代价（如实记）

- `_env.py` 是 `tests/` 下**第一个共享模块**；原先每个测试都是独立脚本。
  ★ 代价是"容器里拷成单文件"那个防御性场景不再成立（该场景**当前不存在**，只是注释里的设想）。
- 已有 4 份 `_dsn` **没有**收编 ⇒ **同一性质仍有 5 处定义**，只是新的那处不会再多。
  这是**未结清的**，不是"已经统一了"。

- ★ **§19 的对拍是「同基准」的**：两边都把 4326 的经纬度当 CGCS2000 用
  （`ST_SetSRID(...,4326)` 再转 4548），手写侧用 GRS80 + 3 度带高斯。
  **跨基准**（WGS84 → CGCS2000）时两个实现**可能合法地不一致** ——
  差异来自基准转换参数，不是投影公式。
  ⇒ 这条判据守的是「**投影公式实现对不对**」，**不是**「基准换得对不对」。
  将来要做后者，得先判「谁该对」，不能直接判红。
- ★ **`crs_family()` 只覆盖「族」这一层粒度**：同族不等于同参数。
  （例：UTM 与 3 度带高斯都是 `tmerc`，但 `_K0` 与带号规则不同。）
  今天只有 `tmerc` 一个族、且模型里只有 3 度带一种带，所以没有暴露；
  **加第二个族时必须同时加一份对拍**（§19 就是那个模板），
  否则新族就是一份没有独立核对的实现。
