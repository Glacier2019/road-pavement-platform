# 契约⑤ · 设计数据导入（Design Data Import）

> 把**任意来源**的道路设计数据装进 GE 域，而不为每一家厂商的格式重写一遍链路。

## 定位说明（待定，勿默认）

本文档是 `contracts/` 下的**第五份契约**，但**暂不并入"四份必认契约"**
（①报文 ②表结构 ③DAO ④服务接口 —— 那是**每个组都必须认**的公共契约，
故 `MODULE-ONBOARDING.md` 等处仍写"四份契约"，未改动）。

理由：本契约约束的是**导入链路内部**（M2 适配器 → IR → 落库），
下游各组消费的是**落库后的 GE 表**（属契约②），不是 IR 本身。
因此它更像 `contracts/fusion/`、`contracts/governance/` 那样的**模块产出契约**。

**是否升格为"必认契约"（四份 → 五份，需同步改 13 处文档表述）由项目负责人决定。**
本文件与测试中称其为"契约⑤"仅作**编号标识**，不代表已进入必认清单。

## 为什么会有这份契约

「导入设计文件」以往是**一次性脚本**：读一遍、填一次库、脚本丢掉。后果有两个：

1. **换一条路就得从头再来**——第二家厂商、第二种格式，全部重写；
2. **没人能证明它读对了**——上一次纬地可行性分析读文件的那段代码没留下来，
   于是"能不能导"只剩一句口头结论，无法复跑、无法回归。

契约⑤ 把这件事拆成三段，**格式差异只影响第一段**：

```
任意来源 ──①采集适配器──▶ 【IR：道路几何中间表示】──②统一校验/质量门──▶ ③落库（经 M2 WriteGuard）
 纬地 / 鸿业 / 图纸 / 反推              格式无关                     只写一遍
```

于是新增一家厂商 = **新增一个适配器**，校验规则与落库路径不动。

## IR 结构

Schema：`road_geometry_ir.v0.3.schema.json`

| 字段 | 含义 |
|---|---|
| `source.vendor` | 厂商标识：`weidi-hintcad` / `hongye` / `manual` / `inferred` |
| `source.origin` | **采集方式**：`file` 厂商数据文件 ／ `manual` 人工录入（含图纸数字化） ／ `inferred` 由既有监测数据反推 |
| `source.files[]` | 逐文件台账（名 / 类别 / `parse_status` / 说明）——对应 `design_file` 表 |
| `capabilities[]` | 本来源**有能力提供**的几何段（适配器声明） |
| `segments{}` | 本次**实际解析出来**的几何段 |
| `gaps[]` | **缺失登记**：能力里有、这次没给出的段 + 原因 |
| `geometry_level` | 几何完整度等级（**推导得出，不允许外部传入**） |

### 段名一律用 GE 域物理表名

`station_sequence` / `station_equation` / `alignment_pi` / `alignment_element` /
`profile_grade_point` / `profile_ground_point` / `geometry_point` / `cross_section`

**不另造一套别名**——段与表的映射唯一，才能自动核对。

### 桩号单位一律「米」

源文件原生单位。换算 km 在落库时做，**避免在 IR 层就丢精度**
（源文件是 3 位小数的米，即毫米级；先转 km 再存 `numeric(10,3)` 会把毫米抹掉）。

## 能力 ≠ 实得：`gaps` 的四种原因

导入**不是成功/失败二元**，而是**按段填充 + 逐段说明缺口**：

| reason | 含义 | 用户的行动 |
|---|---|---|
| `source_absent` | 源里根本没有这一段 | 去找文件 / 接受降级 |
| `parse_blocked` | 有文件但解不开（二进制、需专有工具） | 换工具 / 人工转录 |
| `manual_required` | 需人工录入（如只有图纸） | 走录入模板 |
| `not_supported` | 适配器还没写这段 | 等代码 |

**这四种必须分开。**混成一个"缺纵断面"，用户无从下手——
而"源里没有"和"有但没解出来"的处理方式**完全相反**。

## 几何完整度等级 L0–L4

| 等级 | 含义 | 判据 | 可支撑的下游 |
|---|---|---|---|
| **L0** | 无几何 | — | 几乎无 |
| **L1** | 骨架 | 有 `station_sequence` | 桩号定位、里程统计、逐桩数据挂靠 |
| **L2** | 平面 | L1 ＋ `alignment_pi` 或 `alignment_element` | 线形-车辆运动关联、视距 |
| **L3** | 平纵 | L2 ＋ `profile_grade_point` 或 `profile_ground_point` | 纵坡、排水、超高 |
| **L4** | 平纵横 | L3 ＋ `cross_section` | 横断面/三维（**待 v0.4 第二批**） |

判据在 `adapters/base.derive_level()`，**由实际产出的段推导**。
若让调用方自己填等级，就会出现"填了 L3、实际只有桩号"的假数据。

> 为什么把「平纵」独立为 L3（而不是最初提的"L3 = 平纵横全量"）：
> 横断面表是 GE 完整化的**第二批**，要等 DDL v0.4。若 L3 要求平纵横全量，
> 本工程在 v0.4 之前**永远达不到 L3**，等级就退化成"一直显示 L2"的噪声。
> **一个永远不会变的状态码，比没有更糟。**

## 怎么新增一个适配器

以 `.JD`（平面交点）为例：

1. 写 `adapters/weidi/jd.py`：`detect(text)` + `parse(text) -> {...}`，畸形输入抛 `SourceInvalid`；
2. 在 `adapters/weidi/__init__.py` 的 `IMPLEMENTED` 里加上段名；
3. 在 `tests/contract/test_design_import.py` 增加**应通过 + 应拒绝两侧**的用例；
4. 跑 `./run_contract_tests.sh design`。

⚠ **第 4 步"不用改"只对"该段已在 `segments` 里"成立。** 若新段**不在**契约里，
第 4 步要改成：先给 schema 的 `segments` 加键 + 定义点结构 + 升 `ir_version`（现为 **v0.3**），
再动 `LOADABLE_TABLES`/`plan`/`load`。`.SUP`（超高过渡）就是这么走的 ——
见下节「`.SUP` 与 `.PRJ`：一个进 `segments`、一个不进」。

第 3 步的"应拒绝"一侧不可省：**一个永远不会失败的检查，比没有检查更糟**。
桩号是下游一切逐桩数据的对齐基准，静默读错一条，挂在上面的
WIM / 病害 / 试验数据**全部错位且没有任何报错**。

## 四类来源怎么落

| 来源 | 适配器 | `origin` | 现状 |
|---|---|---|---|
| 纬地 HintCAD | `weidi/` | `file` | ✅ 已实现 7 段：`.STA`/`.JD`/`.pm`/`.DMX`/`.ZDM`/`.SUP`/`.WID`（→ **L3**）；✅ `.PRJ` 项目档案另成一路（见下节）；`geometry_point`/`cross_section` 待做（需 DDL v0.4） |
| 鸿业 | `hongye/` | `file` | 待建 |
| 只有图纸 | `manual/` | `manual` | 待建：人工读图 → 表格模板（桩号、X、Y、R、切线长、转角…） |
| 无文件、只有监测数据 | `inferred/` | `inferred` | 待建：由监测断面实测坐标反推骨架（**只建 `road_line`/`road_section`/`station_sequence`**） |

L1 骨架就足以支撑逐桩数据的挂靠与定位。

## `.PRJ` 总项目文件：它是**档案**，不是几何段 —— 所以不进 `segments`

`.STA`/`.JD`/`.pm` 是几何段，各占 `segments` 的一个键。`.PRJ` **不是**：
它描述的是"这是哪个工程、它有哪些分段属性、它声明用了哪些文件"。

映射关系是**三张表 + 两个路网实体**：

| `.PRJ` 里的东西 | 落到哪 |
|---|---|
| `[项目设置]`（项目名/项目ID/桩号间隔/设计人…） | `design_project`（1 行） |
| `[项目分段N]`（起终点桩号/等级/车速/路幅/横坡/超高/加宽…） | `section_design_attr`（每分段 1 行）+ `road_line` + `road_section` |
| `[文件名]`（声明的文件清单） | `design_file`（每个声明 1 行） |

**为什么不塞进 `segments`**：`segments` 是 `additionalProperties: false` 的 10 个几何段，
而且它的每一项都是"几何点数组"。硬塞一个项目对象进去，schema 就废了。
所以 `.PRJ` 走**独立解析器 + 独立调用**，契约⑤ 的 IR 结构**未作任何改动**。

### `.SUP` 与 `.PRJ`：一个进 `segments`、一个不进

判据只有一条 —— **它是不是"沿桩号的点数组"**：

| 文件 | 是什么 | 进 `segments` 吗 | 为什么 |
|---|---|---|---|
| `.PRJ` | **档案**：工程是谁、有哪些分段属性、声明了哪些文件 | ❌ 不进 | 它不是点数组，是**元数据**。硬塞进去 schema 就废了 → 走独立解析器 + 独立调用 |
| `.SUP` | **逐桩点数组**：每个过渡变化点上 7 个数 | ✅ 进（v0.2 起第 9 段） | 与 `station_sequence`/`profile_ground_point` **同类**；与 `alignment_element` 一样是某个派生量的**真源**（它给 E(s)，`alignment_element` 给 κ(s)） |
| `.WID` | **逐桩号区间数组**：每个区间是「一侧 + 起终点桩号 + 6 个宽度」 | ✅ 进（v0.3 起第 10 段） | 同上**同类**。⚠ 它与前几段有一处不同：**不是逐桩点，是逐区间**（教程 §13.4「每两行为一组，说明路基一侧某个桩号区间内的路幅宽度变化情况」）。判据不变 —— 仍是「沿桩号排列的数组」，故仍进 `segments`；只是落库时把每组的起终点收成 `start`/`end` 两列 |

`.SUP` 因此**改了契约**（v0.1 → v0.2：加段 + 加 `superelev_point` 定义 + 升 `ir_version`）；
`.WID` 同样改了契约（v0.2 → v0.3：加 `roadbed_width` 段 + 加 `roadbed_interval` 定义）。
这与"新增适配器不用改 IR"并不矛盾 —— 那句话的前提是**该段已在契约里**。

**为什么值得单列一段**：`.SUP` 是**过渡转折点**（本工程 76 个），而 `station_sequence`
是**逐桩**（332 个）—— 粒度不同，混成一张表会让"逐桩表里混进了转折点"无从表达。
逐桩的六列横坡是**插值后**的结果，落在 `geometry_point`。

**9999 的语义已用数据独立验证**：教程 §13.5 说 9999 是「可以忽略此数据……系统跳过
此数据的计算继续进行横坡的超高渐变」。实测跨过一个 9999 后，该列的下一个实值
**有时相同、有时改变**（左土路肩 39 同 / 16 变；左行车道 25 同 / 24 变）——
若是"沿用上值"，跨过后应当**全部相同**。数据否决了"沿用上值"，与教程一致。
故解析器把 9999 收成 `null`（`.SUP` 每格非数即 9999，`null` 与"缺值"无歧义）。

### 两段式调用

顺序不是设计选择，是**天生的**：几何表用 FK 锚在 `road_section.id` 上，
路段没建出来就没有 `section_id` 可用。

```python
from adapters.weidi import prj
import design_import as di

out = prj.parse(prj.decode(path.read_bytes()), file=path.name)   # ← 注意 GBK
arch = di.ensure_project(out, dao, project_dir=proj_dir)          # 第一段：档案与路段
sid  = arch["section_ids"][0]["section_id"]
ir   = weidi.build_ir(proj_dir)                                   # 第二段：几何
di.load(ir, dao, section_id=sid, batch_no=...)                    #   （section_start_km 自动从 road_section 读）
```

两段都**幂等**：`ensure_project` 按 `project_uid`/`line_code` 复用，
`load` 按各表的业务键 `on_conflict`。重放不会产生重复行。

### 两个实测踩到的坑

1. **编码是 GBK，不是 UTF-8。** `.PRJ` 是这批文件里**唯一**的 GBK 文件
   （`.STA`/`.JD`/`.pm` 全 ASCII）。按 UTF-8 读会抛 `UnicodeDecodeError`，
   而调用方惯常把它解释成"二进制、不可解析"——**这个结论是错的**，
   它是纯文本。区别"编码不对"与"根本不可解析"很重要：前者换个编码就行。
   适配器用 `ENCODING = "gbk"` 声明，测试里有一条元测试**证明 fixture 按 UTF-8 读确实失败**
   （否则"必须用 GBK"就只是一句注释，不是一个事实）。
2. **`[LONG]/[DOUBLE]/[STRING]` 是二进制块，不是字段。** 它们的键是内存地址
   （`9240611`、`2147418221`），逐行取值毫无意义；组头声明的条数（101/102/103）
   与实际行数也**不相等**，所以"按条数切块"同样不通。解析器显式跳过，
   并把声明条数记进 `ignored_blobs` —— 让"我没解析这块"**可见**，而不是悄悄丢掉。

### 实测（052201341 毕设工程）

`项目名=毕设`（**不是** G228——两条完全不同的路：二级公路/60 km/h/2 车道/5.805 km
vs 一级公路/80 km/h/4 车道/19.701 km）。所以它是**新建一条独立路线**，
而不是挂到既有试验段上。这也正是"宁可拒绝，不要猜"的用处：
挂错了不会有任何报错，只会得到一批归属错误的正常数据。

`.PRJ` 里**没有路线代码**，而 `road_line.line_code` 是 `NOT NULL UNIQUE`——
解析器直接把项目名当代用码，并在 `remark` 里写明这是代用。
编一个看起来像代码的东西，比写清楚"这里没有代码"危险得多。

另有两处**不许猜**的字段：`307路幅宽度 = 10.000` 是**路幅总宽**，
不是单车道宽，所以 `road_line.lane_width_m` 留空、总宽进 `section_design_attr`；
`[文件名]` 里有 12 条空路径槽位、2 条**没有字段号**（涵洞的两个文件），
后者无法满足 `file_kind_code NOT NULL`，故跳过并上报原因。

## ✅ 已解除的两个前置阻塞（2026-09-17 修复）

### 1. 桩号精度装不下真实数据

`.STA` 实测 332 个桩号中 **81 个非 20 m 等距点**（66 种间距），最短间距仅 **0.083 m**：
`1659.917` 与 `1660.000` 在 km 3 位小数下**同为 1.660**，直接撞
`UNIQUE (section_id, station_local_km)` —— **第一次导入就会失败**。

**修法**：14 个桩号列 `numeric(10,3)`/`numeric(12,3)` → **`numeric(12,6)`**（km 6 位小数＝毫米级）。
`station_interval_m numeric(8,2)`（间距用米）语义不同，保持不动。
回归断言在 `test_design_import.py` 第 7 组，并带一条**元测试**证明旧精度确实会碰撞。
实库已重建验证：两条 0.083 m 相邻桩号可同时入库且各自独立。

> 顺带说明：DDL 其实**早已预留加桩概念**（`station_type='jiazi'`、`is_integer_station`），
> 但原精度表达不了它——**预留了字段，没预留分辨率**。

### 2. GE 骨架四表写权为空

`road_line` / `road_section` / `structure_layer` / `monitor_cross_section` 原先未登记
`catalog.TABLE_OWNER` → **只读，任何服务都写不了**，只能靠 `90_seed_skeleton.sql` 种入。
那等于"只能导别人已经种好的路"，与「以后有新的道路文件可以同样导入」直接冲突。

**修法**：四表写权登记为 **M2**（与其余 10 张 GE 表同源：都来自设计文件）。
写权现为 **39 张可写 / 5 张只读**（剩下 5 张是 `dict_*` 字典，种子数据，服务不应写）。
`test_write_guard.py` 已加断言：① 四表必须有 M2 写权；② `SKELETON-GUIDE.md` 里那句
「39 张可写 / 5 张只读」必须与 catalog 一致（**文档硬编码数字是下一个漂移源**，此前那句
长期写着 v0.2 时代的 21/11；后来又因新增 `superelev_transition` 漂了一次 37→38，
再因新增 `roadbed_width` 漂了一次 38→39）。

### 3. `alignment_pi` 的 DDL 列注释标错了值 ✅ **已修正（工单 #3）** —— 但问题比注释更深

`10_ddl_v0.3.sql` 里两行列注释与 `weidi/jd.py` 实测出来的语义**对不上**：

| DDL 注释 | 注释声称的值 | 实测该值其实是 | 真正的值 |
|---|---|---|---|
| `tangent_len_m ... -- 切线长（164.31676725）` | 164.31676725 | **缓和曲线参数 A = √(R·Ls) = √(450×60)** | 切线长 = **117.54242652** |
| `deflection_deg ... -- 转角（-60.0）` | -60.0 | **缓和曲线长 Ls = 60 m** | 转角 = **+22.0027°** |

**怎么证的不是猜的**（`test_design_import.py` 第 8 组逐条断言）：
① 转角由**相邻控制点坐标**独立算出（`atan2(ΔY,ΔX)` 之差），全程不读文件里的角度字段；
② 用该转角算圆弧长 `R(α−2β)` = `112.80868` ＝ 文件里的 `112.80867934`；
③ 用该转角算外距 `(R+ΔR)/cos(α/2)−R` = `8.76417` ＝ 文件里的 `8.76412020`；
④ `√(R·Ls)` = `164.3167672515` ＝ 文件里的 `164.31676725`（10 位小数全中）；
⑤ 切线长 = 交点桩号 − ZH 桩号 = `603.416 − 485.874` = `117.542427` ＝ 文件里的 `117.54242652`。
四条互相独立的等式同时成立 ⇒ 字段归属是**被证明的**。

**为什么两处"互相印证"却谁也没发现**：这两个错值在 DDL 与《数据字典》里**一字不差地各出现一次**，
看起来是两个独立来源对上了，实际**同源**——字典抄的 DDL。
> **"两个文档一致"不构成验证**，除非它们的数据来源相互独立。

**而且问题不止在注释**：A = √(R·Ls) 是纯导出量，却被存成手填列。
它"设计上就该有个值"，所以**没人会去质疑那个值对不对**——把注释改对，冗余还在，下次照样贴错。
学生若照注释实现，会把缓和曲线参数当切线长写进库——**静默写错几何**，正是契约⑤ 要防的事。

**处理（工单 #3）**：
- `alignment_pi` 整体改判为**派生表**（理由见下「4.」）；
- `spiral_a1/a2` 改为 `GENERATED ALWAYS AS (sqrt(radius_m * spiral_lsN_m)) STORED`
  —— 值仍然写出来了（可查、可索引），但 INSERT 根本不允许写它，**结构上不可能与 R、Ls 不一致**；
- 新增 `spiral_ls1_m / spiral_ls2_m`（原始量：原先**只存了导出的 A，没存 Ls**）。
- 新增 `center_x/center_y`、`radius_start_m/radius_end_m`、`end_azimuth_deg`、`section_id`、`length_m`（生成列）到 `alignment_element`；
  **删除其 `curvature_1pm`** —— 缓和曲线单元内 κ 由 0 连续变到 1/R，**不是常数**，一列必然失真。
  （逐桩的 `geometry_point.curvature_1pm` 是**单值**，正确，不动。这个区别是关键。）

### 4. 交点可由单元链**推出** —— 所以 `.JD` 是验算，不是输入

`adapters/geom.py` 的 `derive_control_points(elements)` 只吃单元链。实测
（G228 滨海大道试验段，33 单元 → 8 交点，**`.JD` 一个数都没参与推导**）：

| 字段 | 与 `.JD` 的最大偏差 |
|---|---|
| 交点坐标 x / y | 2.9×10⁻⁸ ／ 1.0×10⁻⁸ m |
| 方位角、转角、半径、Ls、A | **0**（逐位相同） |
| 切线长、交点桩号、圆弧长、曲线总长、前段直线长、特征点桩号 | ≤ 3.6×10⁻⁸ m |
| 外距 | 9.8×10⁻⁹ m |

⇒ 两者不是两份数据，是**同一个东西的两种记法**。折点是线的摘要，两条相邻切线求交即得。

**因此 `.JD` 从「输入」降为「验算」**：一份独立来源的第二意见。两份都在就交叉印证，
不一致就告警／拒绝（走 `warnings` 通道），而不是悄悄采信其中一份。

⚠ **外距不要用教科书的 `(R+ΔR)/cos(α/2)−R`**：那是级数近似，实测对 PI8 差 **1.24 mm**
（一项 ΔR）／0.8 µm（二项 ΔR），而精确几何（圆心 + 角平分线量距离）差 **6×10⁻⁹ m**。
圆心和 HY/YH 坐标都在手边，没有理由用展开式。
测试第 10 组有一条**元测试专门钉住这件事**（断言教科书公式**必须**与 `.JD` 明显不符），
防止以后有人把它"化简"回公式。

**同类问题（尚未处理）**：`geometry_point`（A15 逐桩 κ(s)）**也是派生的** —— 由 A12 + A13/A14 逐桩算出。
它有理由存（缓和曲线要数值积分，逐桩重算代价高），是**合理的缓存**而非冗余；
但必须满足两条：① **可重建**（导入器能一键重算并断言结果一致）；② 与 A12 同批次生成。
DDL 里已标注，落库器要实现。
