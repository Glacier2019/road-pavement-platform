## 2. 接入五件套（逐条可验）

| # | 交付物 | 判据 | 骨架栈的样例 |
|---|---|---|---|
| 1 | 容器定义 | 有 Dockerfile，且在 compose 里有服务段（含 `healthcheck`） | `services/ingest/Dockerfile` |
| 2 | 健康与指标 | `GET /healthz` 逐项报依赖状态；`GET /metrics` 出 Prometheus 文本 | `services/ingest/app.py` `/healthz`、`/metrics` |
| 3 | 配置外置 | 连接串/密钥/端口**全部**来自环境变量或 `config/*.yaml`，代码里零硬编码 | `.env.example` + compose `environment:` |
| 4 | 契约文件 | 本模块消费/产出的 schema、openapi 提交到 `contracts/`，并在本模块 README 登记 | `contracts/messages/wim_axle.v1.schema.json` |
| 5 | 契约测试 | `tests/contract/test_<模块>.py` 可离线跑通，覆盖"应通过/应拒绝"两侧 | `tests/contract/test_wim_contract.py` |

## 3. 数据流向纪律（四条硬线）

1. **对外只经 M6**：模块之间、前端、Copilot、课题组脚本，一律调 `api` 服务取数；**禁止直连数据库**。
2. **写入只经 M2**：任何外部数据（设备、文件、人工录入）必须经接入服务落库，禁止旁路 `INSERT`。
3. **三库分工**：档案/关系 → PostgreSQL；高频时序（>1 Hz）→ IoTDB；文件与影像 → MinIO。
   *骨架期只启 PG，IoTDB 在 P2 随 RE 域接入。*
4. **批次可溯源**：批量导入必须登记 `data_import_batch`，并带 `truth_flag`（默认 `false`，
   由 M4 质量门晋升为真值）。

## 7. 模块验收 DoD（逐条打勾）

- [ ] 五件套齐备，且 `docker compose up -d` 后 `ps` 显示 healthy
- [ ] 契约测试离线通过，且在 CI/本地一键可跑
- [ ] 在**冻结契约**下不改库、不改主题即可接入（若必须改，已开变更工单）
- [ ] 崩溃可恢复：kill 容器后自动重启，且不产生重复数据（幂等/去重已验证）
- [ ] 有日志（含 trace 关联字段）、有指标、有错误分级
- [ ] 数据可溯源：每条输出都能追到 `data_import_batch` 或源记录 id
- [ ] 文档：本模块 README 写清"输入契约 / 输出契约 / 依赖服务 / 失败模式处理"

## 8. 反模式（出现即打回）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 直连数据库查数 | 契约三形同虚设，换库时全线崩 | 走 M6 |
| 模块内私建表 | 表结构失控，设计冻结失效 | 提契约一工单 |
| 硬编码密码/连接串 | 交付物不合规，评委直接扣分 | 环境变量 + `.env.example` |
| 无 `/healthz` | 编排无法判断就绪，故障定位靠猜 | 五件套第 2 条 |
| 把违约数据直接丢弃 | 质量不可证伪，出问题无从追溯 | 进 `data_quality_log` 待检区 |
| 全量重抽（reindex）不审批 | 烧预算、污染已有数据 | 走变更工单 + 记录批次 |
| 用"口头约定"代替契约 | 集成期必然扯皮 | 契约文件 + 契约测试 |
