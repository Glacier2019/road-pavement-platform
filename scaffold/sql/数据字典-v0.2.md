# 路面性能数据库 —— 数据字典 v0.2

> 项目：2025Y095《智慧公路路面结构断面监测与数据融合养护管理技术研究》研究内容（3）
> 配套：`路面性能数据库-DDL-v0.2.sql`（PostgreSQL 方言。v0.1 的 30 表已在本地 postgres 容器 road_ddl_test 库验证可执行：全建、分区插入、复合 FK 全通；
> v0.2 新增 2 表，已在 rp-pg 实库执行并验证幂等（重复执行无 ERROR））
> 命名规范：表=snake_case 复数名词；字段=snake_case；字典表以 `dict_` 前缀；主键统一 `id bigint identity`；时间统一 `timestamptz`；中文说明对齐 T/CECS《高速公路基础设施数据交换技术规程》数据字典风格（字段名/中文名/说明/数据格式）。

---

## 0. 库与双库分工

| 库 | 用途 | 内容 |
|---|---|---|
| `road_pavement`（关系库，本字典） | 档案/字典/事件/聚合/质量/业务 | **32 张表**（A 空间档案 6 + B 字典 5 + C 轴载交通 3 + D 表观病害影像 4 + E 试验 3 + F 模型诊断决策 5 + G 质量反馈 5 + **H 语义映射 1**；v0.2 较 v0.1 新增 G5 `quality_rule`、H1 `mapping_set`） |
| 时序库（独立，IoTDB/TimescaleDB 待选型） | 高频原始序列 | 应变/振动/土压/加速度/挠度/声学/气象分钟流；与关系库按 `channel_id + data_import_batch.id` 对账 |

**分区**：`wim_axle_record`（按月）；高频时序不进关系库（128kHz 单通道日 ≈8.6 亿点，关系库不可行）。特征值/统计聚合落关系库（`traffic_daily_stat`、`ts_feature` 预留）。

## A. 空间与档案（静态基础数据）

### A1. road_line 路线
| 字段 | 类型 | 说明 |
|---|---|---|
| line_code | varchar(32) UNIQUE | 路线代码（G228）|
| line_name | varchar(128) | 路线名称（国道 G228 福清滨海大通道）|
| admin_region / road_class / design_speed | varchar/varchar/smallint | 行政区域 / 公路等级 / 设计速度 |
| design_load | varchar(64) | 设计荷载等级 |
| lane_count / lane_width_m | smallint / numeric | 车道数 3 / 单车道宽 3.75 |
| manage_org | varchar(128) | 管养单位 |

### A2. road_section 路段
`line_id→road_line`；start/end_stake（K4635+000 文本桩号）+ start/end_km（4635.000 数值桩号，便于区间检索）；length_m；direction；pavement_type；climate_zone。

### A3. structure_layer 路面结构层（断面分层核心）
`section_id` + `layer_no`（自上而下 1..n）+ layer_name（AC-13C 改性沥青抗滑表层）+ layer_role（面层/基层/底基层/路基）+ material + thickness_cm。
> 实测例：4cm AC-13C / 6cm AC-20C / 12cm ATB-25 / 16cm 级配碎石 / 1cm 沥青表处 / 32cm 5%水稳底基层 —— 数字孪生分层可视化的结构依据。

### A4. monitor_cross_section 监测断面
| 字段 | 说明 |
|---|---|
| section_id / stake_text / stake_km | 路段 / 桩号 K4635+710 / 4635.710 |
| lane_no / lon / lat | 车道 / CGCS2000 坐标 |
| purpose | 用途（轴载调查/结构响应/应变断面）|
| install_date / status | 埋设日期（2025）/ active |

### A5. sensor_install 传感器布点
| 字段 | 说明 |
|---|---|
| cross_section_id | 所属断面 |
| sensor_type_code | →dict_sensor_type（石英称重/线圈/应变计/土压力盒/三向加速度/钢筋计/温湿度/风速风向/雨量/辐射/紫外/传声器/视觉相机/视频球机/光纤）|
| sensor_model / manufacturer / serial_no | 型号（ZDG-40-SY-2）/厂家/出厂编号 |
| install_mode | 埋入式/表面式/车载式/非接触 |
| structure_layer_id / install_depth_cm | 埋设层位（内观定位）/ 深度 |
| install_date / status | 安装日期 / active-fault-lost-retired |

### A6. sensor_channel 监测通道（逻辑测点）
| 字段 | 说明 |
|---|---|
| install_id + channel_no | 布点 + 通道号（三向加速度=3 通道），UNIQUE |
| quantity_code | →dict_quantity（应变/应力/土压/加速度/温度/湿度/雨量/挠度/声压级）|
| unit / range_low / range_high | 单位 / 量程（应变计 ±5000με）|
| sample_rate_hz | 采样率（1k~128k 分档）|
| acquire_mode | continuous 连续 / trigger 自动触发 / periodic 定时 |
| storage_policy | full 全存 / feature 特征值 / ratio 稀释 |
| dilution_rule jsonb | 稀释规则（PHM「分析点数/稀释比例自定义」落地）|

> ⚠️ 关系库↔时序库关联键：`sensor_channel.id`。

## C. 轴载与交通（WIM 事件数据）

### C1. wim_axle_record 车辆轴载记录 ⭐分区表（按月）
| 字段 | 说明 |
|---|---|
| id + pass_time | PK (id, pass_time)——分区表 PK 含分区键 |
| cross_section_id | 监测断面（轴载调查站位）|
| lane_no / direction | 车道 / up-down |
| axle_type_code →dict_axle_type | 轴型 |
| axle_num / speed_kmh | 轴数 / 车速（1~200km/h，±1km/h）|
| gross_weight_kg | 总重（单轴 30t，过载 200%）|
| overload_flag / overload_rate | 超载标记 / 超载率（30%/50% 统计口径）|
| esal | 当量轴次 |
| plate_no / video_media_id | 车牌（与抓拍匹配）/ 影像 |
| data_source / quality_code | 采集设备溯源 / OK-ERR-UNCERTAIN |

索引：`(pass_time)`、`(axle_type_code, pass_time)`、UNIQUE `(id, pass_time)`（供 FK）。
⚠️ 生产需**脚本化提前建 12 个月分区 + 默认分区**，否则新月份数据插入报「no partition found」。

### C2. wim_axle_detail 轴组明细
`record_id + pass_time` 复合 FK→主表（分区表引用必须带分区键）；axle_seq 轴序；axle_weight_kg 轴重；group_weight_kg 轴组重；axle_dist_mm 轴距（±100mm）。UNIQUE(record_id, axle_seq)。

### C3. traffic_daily_stat 交通量日统计
按断面×日期 UNIQUE；total/truck/heavy/overload/overload30/overload50 计数；esal_total；by_axle_type jsonb 分轴型计数（{"A2":2434,"T6":8805}）；overload_by_axle jsonb 超载占比（对齐开题表 5/6 统计口径，科研免扫明细）。

## D. 表观普检 / 病害 / 影像

### D1. inspect_task 巡检任务
task_type（scan3d 三维高精扫描 / ai_vehicle 车载 AI / manual / uav）；task_time；vehicle_no；route_desc 覆盖范围；org；status。

### D2. disease_record 病害记录
task_id→D1（可空=历史导入）；section_id + stake_text/stake_km + lane_no 定位；disease_code→字典；severity light/moderate/severe；length/width/area 尺寸；image_media_ids jsonb；source；status pending/processing/done；first_seen（病害演变观测起点）。
索引：`(section_id, stake_km)`、`(disease_code)`。

### D3. scan3d_model 三维扫描模型
section_id；scan_time；file_path（**文件外置，库存索引**）；precision_mm（毫米级）；coverage_from/to 覆盖桩号；size_bytes。

### D4. media_file 影像/文件元数据（通用附件）
biz_table + biz_id 多态关联；media_type image/video/model/doc；file_path/file_name/size；width/height/duration；taken_time；stake_text；md5。
> 对应「图像数据」全量管理：病害图、巡检视频、过车抓拍、监测视频、扫描模型。

## F. 模型输出 / 诊断 / 预警 / 养护决策

### F1. model_output 模型/仿真输出
object_type + object_id 多态指向（section/cross_section/channel/network）；model_code（FEA_static / FEA_dynamic / LLM_pred / life_pred）；output_type（theory_strain / theory_stress / deflection / pci / 寿命 / 风险）；calc_time；value 标量 + value_json 复杂结果；params jsonb 工况；source_batch。
> ⭐「测试值与有限元计算值相结合」预警机制的理论值来源表。

### F2. diagnosis_result 融合诊断结果
object_type/object_id；diagnose_time；method_code（融合辨析/健康诊断模型）；conclusion_code healthy/watch/warning/risky；conclusion 结论文本；confidence 置信度；basis_summary 依据摘要；report_media_id。

### F3. maintenance_advice 养护决策建议
diagnosis_id→F2；advice_type（preventive 预防性养护 / repair / strengthen **补强强化** / monitor 加密监测）；content；priority 1~5；cost_est 万元；status；effect_feedback（养护效果实时监测反馈→优化计划）。
> 手稿「强化/承载力评估」+ 预防性养护调控输出落点。

### F4. alarm_rule 预警规则
channel_id（通道级可空）；rule_type overrun/rate/trend/spectrum/ml（超限/变化率/趋势/图谱对比/机器学习）；params jsonb（阈值——应变预警值来自 FEA 对照）；push_channel。

### F5. alarm_record 预警记录
rule_id；channel_id；alarm_time；level **yellow/red**（黄红二级）；actual_value/threshold；status unconfirmed/confirmed/handled。
索引：`(alarm_time)`、`(channel_id, alarm_time)`。

| **mapping_set**〔v0.2 新增〕 | **语义映射集（M7 语义中枢）**：`mapping_id`+`version`（UNIQUE）、`source_kind`（表头/桩号/单位/编码，解决哪一类「不对应」）、`source_sample` 样表来源、`source_hash` 源结构指纹（同结构可复用映射，不必再问人）、`target_table`、`entries jsonb` 映射条目 `[{raw,normalized,target_field,unit,transform}]`、`status`（候选/已确认/已废弃）、`confirmed_by/at`、`proposed_by`（rule/llm/human）、`confidence`。约束：**status=已确认 必带确认人与时间** |

## 时序库建模要点（IoTDB 优先评估）

```
存储组 root.road.<line_code>         例 root.road.g228
序列    root.road.g228.<stake>.<install_id>.<quantity>
        root.road.g228.k4635710.s1001.strain
        root.road.g228.k4635710.s1001.accel_x
特性    1. 原始层 TTL 滚动（保留 1~2 周）+ 特征值层永久（min/max/mean/rms/std/p95，对齐 dict_stat_metric）
       2. 高频（应变/振动）与分钟级（气象）分存储组，避免压缩率互拖
       3. 写入幂等去重（时间戳+通道唯一）
       4. 批次号贯穿两侧对账（data_import_batch.id）
```
TimescaleDB 备选（同生态）：`ts_sample(channel_id, ts, value, quality)` + hypertable 按日 chunk；128kHz 单通道日 8.6 亿点需原始+稀释双层。
