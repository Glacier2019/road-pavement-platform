对标 Palantir 的关键，不是"做出一个 Foundry"，而是**把平台定位从"数据库底座"改成"决策中心的本体系统"**——Palantir 自己反复强调的那句话是：Ontology 不只是数据模型，而是把 **数据 + 逻辑 + 动作 + 安全** 四要素装进同一个系统（语义元素 = objects/properties/links，动能元素 = actions/functions/security）。

## 一、Palantir 的架构事实（可对标对象）

- 三平台：**Foundry**（数据运营 + 本体 + 工作流）、**AIP**（生成式 AI，k-LLM 多模型路由 + Agent + Evals）、**Apollo**（跨环境持续交付）
- 本体 = **Object Type / Property / Link Type / Interface**（语义） + **Action Type / Function / Dynamic Security**（动能）
- **Action** 是它的护城河之一：不是写数据库，而是"受治理的事务"——参数校验 + 权限 + 副作用（通知）+ 写回源系统（writeback dataset），所有应用共用同一套动作逻辑
- Agent 不碰数据库：**Ontology-Augmented Generation（OAG）**，五层 = 上下文注入（系统决定）→ 对象/关系查询 → 函数调用 → 受治理动作 → 治理贯穿（marking/purpose/role 三重策略 + 动态血缘 + 审计）；设计哲学"确定性优先、必要处自治、处处约束"
- 参考：docs `foundry/ontology/overview`、`action-types/overview`、`architecture-center/platforms`、Palantir Blog《Connecting Agents to Decisions》与 OAG 五层架构分析

## 二、逐层对标：我们有什么 / 缺什么 / 怎么补

| 层 | Palantir 做法 | 我们现状 | 缺口动作 |
|---|---|---|---|
| **本体（语义）** | 表→Object Type，外键→Link，字段→Property | ER 25 表 + 第九章已补 21 类关系字典、指标三元 | **把表"对象化"**：出一份《本体对象类型清单》（对象类型/属性/链接/枚举），ER 图表升级为对象-链接图 |
| **逻辑资产** | Function Tool：ML/优化/仿真都封装成可调用函数（LLM 不做算术） | FEM 正演、代理模型、融合辨识算法散在 M 模块里 | 每个模型注册为**函数契约**（输入对象集 / 参数 / 输出对象或属性）——这也正好是学生课题 B/C/D 的接口定义 |

## 一、形态：方法论一致，产品形态不一致

| 维度 | Palantir | 我们（2025Y095） | 判断 |

| 智能体方式 | OAG：agent 只碰本体对象/函数/动作，不碰库表 | 双 Copilot 目前还是字段映射+检索，**缺工具层** | ◐ 有差距但可补 |

## 一、第一步是什么

**不写业务代码，先造一条能跑通的竖切（walking skeleton）**：让一条 WIM 过车报文从造数器出发，经 EMQX → 接入服务 → PG 分区表 → 出口 API → Grafana 走完全程。

```
simulator → EMQX → ingest(M2) → PostgreSQL 分区表 → api(M6) → Grafana
```

选 LO 域（WIM）作切口，理由是可判定的：秒级事件、报文结构简单、`wim_axle_record` 分区表已实测、不碰 IoTDB、不占 GPU、能造数。RE 应变（要 IoTDB）和 SU 图像（要 GPU）都推到 P2/P3。

## 三、模块接入怎么组织

规则写在 `MODULE-ONBOARDING.md`：**认三份契约 + 交五件东西 + 过一道门**。

五件东西：Dockerfile/compose 段、`/healthz`+`/metrics`、外置配置、契约文件、契约测试。
三条硬线：取数只经 M6、写入只经 M2、三库分工（PG 档案 / IoTDB 高频 / MinIO 文件）。
顺序铁律：**下游不启动，直到上游两个契约测试都绿**。契约变更走工单模板（含破坏性变更的迁移与回滚），"口头说一声改个字段"一律不算。
